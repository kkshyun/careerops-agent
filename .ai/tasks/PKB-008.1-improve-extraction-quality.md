## Context

VALIDATE-001(수동 E2E)에서 실제 사용자 문서(이력서/경험정리)를 PKB-008
extraction 파이프라인에 넣어본 결과, MATCH-001을 검증하기 전 단계인 LLM
구조화 추출 자체의 품질/안정성 문제가 확인됐다:

- 이력서: CareerExperience 2건만 candidate 생성(원문에 자격증 8개·학력
  2건이 명시돼 있었는데 Certification/Education/Award 0건). 생성된
  CareerExperience도 title/organization/role만 채워지고 summary/detail/
  tags는 비어 있었으며, startDate/endDate에 원문과 무관한
  `2000-01-01`/`2200-01-01`이 채워짐.
- 경험정리(rawText 약 1만자): extraction이 3회 전부 400
  `MALFORMED_RESPONSE`로 실패(`AnthropicDocumentExtractionClient.MAX_TOKENS
  = 8_192` output 상한 관련으로 추정).

이번 Task는 이 근본 원인을 고쳐 "원문에 명시된 사실은 근거 없는 값 없이
안정적으로 candidate로 추출"되게 만드는 것이 목표다. **MATCH-001 채점
로직, OCR, LLM reranking, embedding은 이번 범위 밖이다.**

## Root Cause (구현 전 조사로 확정 — 추측 아님)

Anthropic Java SDK(`com.anthropic:anthropic-java:2.54.0`)의
`outputConfig(Class)` 자동 schema 유도 로직을 SDK 소스
(`StructuredOutputs.kt`, GitHub `anthropics/anthropic-sdk-java`)에서 직접
확인했다:

```kotlin
.withRequiredCheck { true }   // 모든 필드를 예외 없이 "required"로 강제(override 불가)
.withNullableCheck { field -> if (field.isMarkedNullable()) true else null }
```

- 모든 레코드 필드가 Bean Validation(`@NotBlank` 등)과 무관하게 JSON
  스키마에서 **항상 required**로 취급된다.
- 필드 타입이 `["string","null"]`처럼 null을 허용하려면 그 필드에
  **`@Nullable`(단순 이름이 정확히 `Nullable`인 어떤 annotation이든,
  `RUNTIME` retention 필수) annotation이 있어야만** 한다.
- 우리 DTO(`CareerExperienceCreateRequest` 등)는 어디에도 `@Nullable`이
  없는 순수 Java record라, 모든 optional 필드가 "반드시 존재해야 하고
  null도 안 되는" 필드로 스키마에 강제된다.

결과: 모델이 날짜를 모를 때 이를 표현할 합법적인 방법이 없어(생략도
null도 불가) `2000-01-01`/`2200-01-01` 같은 값을 지어냈다. Certification/
Education/Award도 같은 이유로, issuer/expirationDate/credentialId 등을
지어내는 대신 객체 전체를 결과에서 누락시킨 것으로 보인다(system prompt의
"사실 없으면 지어내지 마라"와 schema의 "모든 필드 채워라"가 충돌했고,
모델이 그때그때 다른 방식으로 회피).

기존 PKB-008 테스트(`AnthropicDocumentExtractionClientTest` 등)는
`DocumentExtractionClient` 인터페이스를 fake로 교체해 실제 schema 유도
경로를 전혀 통과하지 않으므로 이 문제를 잡을 수 없는 구조였다 — 이번
Task에서도 이 사실 자체는 바뀌지 않는다(자동 테스트는 여전히 실제
Anthropic API를 호출하지 않는다, §Test Plan).

`MAX_TOKENS=8_192`는 **output token 상한**(input context와 무관)이라,
CareerExperience 여러 건 + summary/detail/tags/bullets가 함께 채워지는
긴 문서에서 JSON이 중간에 잘려 파싱 실패(`AnthropicInvalidDataException`
→ `MALFORMED_RESPONSE`)로 이어졌을 가능성이 높다(코드 경로상
`MALFORMED_RESPONSE`는 정확히 "모델 텍스트를 T로 파싱 실패"할 때만
발생 — 잘린 JSON과 정확히 일치하는 증상).

## Scope

### 1. Nullable 구조화 스키마 (최우선)

다음 5개 기존 DTO에서 **현재 `@NotBlank`/`@NotNull`이 없는 필드 전부**에
`org.jspecify.annotations.Nullable`을 추가한다(List 타입 필드는 빈
배열로 "없음"을 표현할 수 있으므로 제외):

- `CareerExperienceCreateRequest`: `organization`, `role`, `startDate`,
  `endDate`, `summary`, `detail` (`type`/`title`은 그대로 required 유지,
  `bullets`/`tags`는 List라 제외)
- `CertificationCreateRequest`: `issuer`, `acquiredDate`,
  `expirationDate`, `credentialId`, `description` (`name`은 required 유지)
- `EducationCreateRequest`: `major`, `degree`, `status`, `startDate`,
  `endDate`, `gpa`, `gpaScale`, `description` (`institution`은 required
  유지 — `degree`/`status`는 enum이지만 이미 Bean Validation에서
  `@NotNull`이 없어 도메인상 optional이므로 동일 원칙 적용)
- `AwardCreateRequest`: `issuer`, `awardedDate`, `description` (`title`은
  required 유지)
- `ExperienceBulletRequest`: `bulletType` (`content`는 required 유지)

새 dependency: `org.jspecify:jspecify:1.0.0`을 `build.gradle`에 명시
추가한다(`implementation`, compile+runtime 모두 필요 — SDK가 런타임
리플렉션으로 annotation을 읽는다). 현재도 `anthropic-java`의 전이
의존성으로 classpath에 이미 존재하는 라이브러리를 명시 선언하는
것뿐이며, 새로 받는 외부 코드가 아니다(사용자 승인 완료 — 이유를
ADR에 기록).

**검증(필수)**: 이 스키마 변경이 실제로 의도대로 생성되는지, fake
`DocumentExtractionClient` 우회 없이 직접 확인하는 테스트를 추가한다
(예: SDK의 schema 유도 함수를 호출해 특정 필드가
`"type":["string","null"]`이고 `"required"` 배열에 포함되어 있는지 assert
— 실제 Anthropic API 호출은 아니고 로컬 schema 생성만 실행). 이 테스트가
없으면 향후 SDK 업그레이드나 DTO 필드 추가 시 이번 수정이 조용히
깨질 수 있다.

### 2. Prompt v2

`ExtractionPromptBuilder`의 `PROMPT_VERSION`을 `"v2"`로 올리고 system
prompt를 다음 의도로 재작성한다(기존 hallucination/injection 방지 원칙은
전부 유지):

1. 문서 전체를 CareerExperience/Certification/Education/Award **4개
   카테고리 각각에 대해 독립적으로** 훑는다(하나만 먼저 찾다가 나머지를
   놓치지 않도록 명시).
2. 발견한 명시적 사실은 누락하지 않는다.
3. 원문에 없는 사실은 생성하지 않는다(기존 원칙 유지).
4. 값을 모르면 null(기존 원칙 유지) — 예시를 구체화한다:
   - `"2025년 여름"` → null
   - `"2025.07"`(연-월만, 정확한 일자 모름) → null(임의로 1일을 넣지
     않는다)
   - `"2025-07-19"`(정확한 연-월-일) → 그대로 사용
5. tags는 원문에 **명시적으로 등장한** 언어/framework/DB/infra/AI-ML
   기술/주요 개발 기술만 담는다("백엔드니까 AWS도 썼겠지" 같은 추론
   금지 — 예시를 프롬프트에 포함).
6. summary/detail은 새로 각색하지 않고 원문 사실을 압축/정리하는
   수준으로만 채운다.
7. 결과를 설명하지 않고 schema만 반환한다(기존 원칙 유지).
8. `documentType`은 힌트일 뿐 targetType을 제한하는 필터가 아니다
   (예: EXPERIENCE_NOTE에도 Certification이 명시돼 있으면 추출한다).

`<document>` 태그 격리, "오직 이 system 지시만 따른다" 등 기존
injection 방지 문구는 그대로 유지한다.

### 3. Output token 예산 재조정

- `AnthropicDocumentExtractionClient.MAX_TOKENS`를 `8_192` →
  `16_000`으로 올린다.
- `application.yml`의 `careerops.ai.request-timeout-seconds`를 `60` →
  `120`으로 올린다(더 큰 maxTokens에 비례한 여유, 무한 대기는 여전히
  금지 — 명시적 timeout 유지).
- `StructuredMessage.stopReason()`(SDK가 실제로 노출함, `javap`으로
  확인 완료)을 확인해 `stopReason() == StopReason.MAX_TOKENS`인 경우를
  구분 가능한 형태로 다룬다 — 원문/응답 내용 없이 enum 값만 사용(§Privacy
  원칙 유지). 반드시 새 `LlmExtractionException.Reason`을 추가할 필요는
  없으나(기존 `MALFORMED_RESPONSE` 매핑을 유지해도 무방), 최소한 이
  경우를 구분해 향후 진단이 가능하도록 한다 — 정확한 처리 방식(새
  Reason 추가 vs 기존 분류 유지 + 관찰 가능성만 개선)은 Codex가 기존
  코드 스타일에 맞춰 판단하되, **원문/모델 응답 텍스트는 어떤 경우에도
  로그에 남기지 않는다.**

### 4. 좁은 조건의 Chunking (50,000자 상한 지원)

`SourceDocument.rawText` 상한은 여전히 50,000자다(변경 없음). 모든
문서를 chunk하지 않는다 — **20,000자 미만은 기존처럼 단일 요청**,
그 이상만 chunk한다.

신규 클래스 2개:

- `DocumentChunker`: `List<String> chunk(String rawText)`. 문단/개행
  경계(빈 줄 기준)로 분리한 뒤, 약 12,000자를 목표로 그리디하게
  chunk를 패킹한다(각 chunk가 목표 크기를 넘기 전까지 문단을 계속
  추가). 단일 문단 자체가 목표 크기보다 크면 그 문단만 강제로
  분할한다(fallback, 드문 경우). **겹침(overlap) 없음** — chunk 경계는
  문단 경계와 정확히 일치한다.
- `ChunkingDocumentExtractionClient implements DocumentExtractionClient`:
  생성자로 실제 `AnthropicDocumentExtractionClient`(구체 타입)와
  `DocumentChunker`를 주입받는다. `rawText.length() < 20_000`이면
  그대로 위임(현재 동작과 100% 동일). 그 이상이면 `DocumentChunker`로
  나눈 뒤 각 chunk에 대해 순서대로
  `delegate.extract(chunkText, documentType)`를 호출하고, 4개
  `List<...CreateRequest>`를 chunk 순서대로 concat한다. **청크 하나라도
  실패하면(어떤 `LlmExtractionException`이든) 그 즉시 예외를 그대로
  전파하고 남은 청크는 호출하지 않는다**(전체 extraction 실패로 이어져
  기존 all-or-nothing 정책이 그대로 유지됨 — `ImportBatchExtractionService`
  는 이 클래스를 수정 없이 그대로 사용할 수 있어야 한다).
- 병합 시 최소 dedup: concat된 리스트에 대해 `List<T> deduped =
  list.stream().distinct().toList()`처럼 **완전히 동일한 구조화
  객체**(record의 자동 `equals()`)만 제거한다(순서는 첫 등장 순서
  유지). semantic dedup/embedding 기반 dedup은 하지 않는다.
- Spring 배선: `AnthropicDocumentExtractionClient`는 그대로 `@Component`
  (더 이상 `@Primary`일 필요 없음). `ChunkingDocumentExtractionClient`가
  `@Primary @Component`로 `ImportBatchExtractionService`에 주입된다.
  `ImportBatchExtractionService`, `ImportBatchController`, API contract
  (`POST /api/career/imports/batches/{id}/extract` 요청/응답, batch당
  1회 재실행 정책)는 **전혀 수정하지 않는다** — 이 클래스는 인터페이스
  뒤에서 한 번만 호출되므로 orchestration 계층은 chunking의 존재를
  몰라도 된다.

### 5. PlaceholderValueSanitizer 보강

기존 placeholder 문자열 집합 `{"현재", "미상", "해당없음", "해당 없음",
"n/a", "unknown", "없음"}`에 `"-"`, `"tbd"`(대소문자 무시)를 추가한다.
날짜 필드 전용 placeholder 로직은 추가하지 않는다(§1의 nullable schema
+ §2의 prompt 예시로 이미 방지되며, 날짜 필드는 LocalDate 타입이라
잘못된 문자열이 들어오면 역직렬화 자체가 실패해 자연히 all-or-nothing
경로로 이어진다 — 기존 PKB-008 설계 원칙 유지).

## Technical Notes

- 최우선 참고 자료: 이번 Task 조사에서 직접 확인한 Anthropic SDK 소스
  `StructuredOutputs.kt`(`anthropics/anthropic-sdk-java` GitHub
  `main` 브랜치, `anthropic-java-core/src/main/kotlin/com/anthropic/core/`
  경로) — `withRequiredCheck { true }`/`withNullableCheck`/
  `hasNullableAnnotation`/`isNullableKotlinProperty` 함수 전체를 읽고
  `@Nullable`이 정확히 어떤 조건(단순 이름 일치, RUNTIME retention,
  필드/getter의 annotated type 포함)에서 인식되는지 구현 전에 반드시
  재확인한다(SDK가 마이너 업데이트로 바뀌었을 수 있으므로 Codex가
  구현 시점에 실제 jar를 다시 확인).
- `org.jspecify.annotations.Nullable`의 retention/target은 `javap`으로
  직접 확인 완료: `@Target(TYPE_USE)`, `@Retention(RUNTIME)` — SDK의
  인식 조건을 정확히 만족한다.
- `StructuredMessage.stopReason()`/`usage()`는 `javap`으로 존재를 확인
  완료(`com.anthropic.models.messages.StructuredMessage`) — 실제 API
  호출 없이도 시그니처만으로 사용 가능함이 확인됨.
- `ChunkingDocumentExtractionClient`는 `AnthropicDocumentExtractionClient`
  구체 타입을 생성자로 주입받아 delegate로 사용한다(인터페이스가 아닌
  구체 타입 주입 — provider가 하나뿐이므로 ADR-0024의 "provider
  registry/factory 만들지 않는다" 원칙과 일치, 과도한 추상화 방지).
  단, 단위 테스트에서는 fake `DocumentExtractionClient`를 delegate로
  주입할 수 있도록 생성자 파라미터 타입을 인터페이스로 받는 오버로드나
  테스트 전용 생성자를 고려할 수 있다(Codex 판단, 과하게 만들지 않는다).
- 신규 production dependency: `org.jspecify:jspecify:1.0.0` 1개
  (`implementation`) — 이미 `anthropic-java`의 전이 의존성으로 classpath
  에 존재하던 것을 명시 선언하는 것이며, 사용자 승인 완료. ADR에 이유를
  기록한다.
- 테스트에서 실제 Anthropic API를 호출하지 않는다(§1의 schema 검증
  테스트도 로컬 schema 생성 함수만 실행하며 네트워크 호출은 하지
  않는다 — SDK의 `extractSchema`류 내부 함수가 `internal` 가시성이라
  직접 호출이 안 되면, 우리 DTO에 리플렉션으로 `@Nullable` annotation이
  실제로 붙어 있는지 확인하는 테스트로 대체 가능 — Codex가 구현 시점에
  SDK의 실제 접근 가능한 API를 확인해 가장 신뢰도 높은 방법을 선택한다).
- 자동 테스트에는 실제 이력서/경험정리 문서를 넣지 않는다. 합성
  fixture로 다음을 재현한다: Experience+Certification 여러 개+Education
  여러 개+Award가 섞인 문서, 정확한 날짜가 없는 경험, 연/월만 있는
  날짜, 기술 tag가 명시된 경험, 긴 EXPERIENCE_NOTE(chunk 트리거용,
  20,000자 이상 — 로렘input 아니라 chunk 경계 테스트에 적합한 반복 구조
  텍스트로 충분, 실제 개인정보 아님).
- 실제 사용자 문서는 자동 테스트 통과 후 수동 E2E(§Acceptance Criteria
  `[수동]` 2건)에서만 사용한다.
- dev DB 정리가 필요하면(§Acceptance Criteria `[수동]` 참고) 정확한

  `import_candidates`/`import_batches`/`source_documents`)만 특정해
