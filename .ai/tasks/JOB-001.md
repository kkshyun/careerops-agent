## Context

`docs/ROADMAP.md` Phase 1 완료(CORE-001)로 백엔드 실행 기반(Spring Boot +
PostgreSQL/Redis + Actuator)이 마련됐지만, 저장소에는 아직 도메인 코드가
전혀 없다(`BackendApplication` 하나뿐). 이 Task는 CareerOps가 다루는 첫
실제 도메인인 **채용공고(Job Posting)** 의 최소 저장/조회 기능을 만들어,
"애플리케이션 코드가 실제 데이터를 다루고, DB에 쌓이고, API로 오가는" 첫
수직 slice를 완성한다.

`docs/PROJECT.md`의 목표 1(채용공고 자동 수집)로 가는 전 단계이지만, 이번
Task는 수집(크롤링)을 하지 않는다. 향후 JOB-ALIO, 기업 공식 사이트, 금융사
공식 사이트 등 여러 출처를 연결할 예정이므로, 지금은 "그 데이터를 받아
저장/조회할 수 있는 최소 모델 + API"만 만든다. 데이터는 이번 Task
범위에서는 API로 직접 생성(수동/테스트)한다.

## Scope

1. `JobPosting`을 PostgreSQL에 저장할 수 있다(JPA Entity + Repository).
2. 저장된 `JobPosting` 하나를 ID로 조회할 수 있다.
3. REST API 2개만 구현한다: `POST /api/jobs`(생성), `GET /api/jobs/{id}`(단건
   조회). 목록조회/검색/수정/삭제는 만들지 않는다.
4. 최소 필드(회사명, 제목, 출처)에 대한 입력 검증 — Bean Validation.
5. Persistence 및 API 동작을 실제로 검증하는 자동 테스트 — CORE-001의
   `contextLoads()` 수준으로는 불충분. 저장→조회 흐름을 실제로 검증한다.
6. Job Posting 관련 최소 product metric 계측(`careerops_job_creation_total`,
   `careerops_job_read_total`) — Micrometer, `/actuator/prometheus`로 노출.
7. CORE-001의 Actuator health/prometheus 동작을 그대로 유지(회귀 없음).
8. DB 스키마는 Hibernate 자동 생성이 아니라 Flyway 마이그레이션으로
   관리한다(근거: `docs/DECISIONS.md` ADR-0006).

- Lombok, MapStruct 등 신규 편의 라이브러리 — 이번 Task 규모(Entity 1개,
  DTO 2개)에서는 보일러플레이트 비용이 낮아 도입 근거가 부족하다(Technical
  Notes 참고). 필요성이 명확해지는 시점(Entity/DTO 수가 늘어나 반복 비용이

- Testcontainers, CI 파이프라인 — CORE-001과 동일하게 로컬 Docker Compose
  PostgreSQL을 테스트 사전조건으로 사용한다(Test Plan 참고). 아직 CI 자체가
  없다.
- `applicationStartAt`/`applicationEndAt` 간 대소 관계 등 cross-field
  business validation — 최소 필드 검증(필수값 존재 여부) 범위를 넘어서므로
  이번엔 하지 않는다.

## Acceptance Criteria

검증 방식을 `[자동]`(스크립트/명령으로 기계적으로 확인 가능) /
`[수동]`(사람이 직접 확인해야 함)으로 표시한다. 모든 자동 테스트는
저장소 루트에서 `docker compose up -d`로 PostgreSQL/Redis가 기동 중이어야
한다는 CORE-001의 사전조건을 그대로 따른다.

- [ ] `[자동]` **생성 성공**: `POST /api/jobs`에 최소 필수 필드
      (`companyName`, `title`, `source`)를 포함한 유효한 JSON을 보내면
      `201 Created`와 함께 응답 본문에 서버가 생성한 `id`, `createdAt`
      및 요청에 포함된 필드 값이 그대로 포함된 JSON을 반환한다.
- [ ] `[자동]` **생성 검증 실패**: `companyName`, `title`, `source` 중
      하나라도 비어있거나(blank) 누락된 요청을 `POST /api/jobs`로 보내면
      `400 Bad Request`를 반환하고, 해당 `JobPosting`이 DB에 저장되지
      않는다.
- [ ] `[자동]` **조회 성공**: 방금 생성한 `JobPosting`의 `id`로
      `GET /api/jobs/{id}`를 호출하면 `200 OK`와 함께 생성 시 저장한 필드
      값과 동일한 JSON을 반환한다.
- [ ] `[자동]` **조회 실패(존재하지 않는 id)**: 존재하지 않는 `id`로
      `GET /api/jobs/{id}`를 호출하면 `404 Not Found`를 반환한다.
- [ ] `[자동]` **Repository 저장/조회 흐름 검증**: `JobPostingRepository`에
      대한 테스트에서 `save()` 후 `findById()`로 동일 엔티티를 조회하면
      저장 시점의 필드 값과 일치한다(단순 `contextLoads()`가 아닌 실제
      데이터 흐름 검증).
- [ ] `[자동]` **Flyway 마이그레이션 자동 적용 + 스키마 일치**:
      `spring.jpa.hibernate.ddl-auto=validate` 설정 하에서 애플리케이션
      컨텍스트가 정상 기동한다(즉, Flyway가 만든 실제 스키마와 `JobPosting`
      엔티티 매핑이 일치함이 기동 성공으로 증명된다). 불일치 시 컨텍스트
      기동이 실패해야 하므로, 이 자체가 자동 검증이다.
- [ ] `[자동]` **Product Metric 계측 확인**: 애플리케이션 기동 후

## Technical Notes

### 1. JobPosting 필드 설계 (최종)

사용자가 제시한 "표현 가능해야 할 개념" 목록을 그대로 필드로 옮기지 않고,
아래와 같이 판단했다.

| 필드 | 타입 | 필수 | 선정 이유 |
|---|---|---|---|
| `id` | `Long` | (자동 생성) | PK. `IDENTITY` 전략(Postgres native identity/serial과 자연스럽게 매칭). |
| `companyName` | `String` | **필수** | 회사. 별도 `Company` Entity로 분리하지 않고 문자열로 단순화(아래 "Company 분리 여부" 참고). 핵심 식별 정보이므로 필수. |
| `title` | `String` | **필수** | 공고 제목. 핵심 식별 정보이므로 필수. |
| `employmentType` | `String` (nullable) | 아니오 | 채용 형태(신입/인턴/경력 등). 소스마다 표기가 다를 것으로 예상되어(예: ALIO "신입/경력", 기업 사이트 "체험형 인턴" 등) 지금 enum으로 정규화하면 추측에 기반한 정규화가 된다. 실제 소스 2곳 이상이 붙기 전까지는 자유 문자열로 저장하고, 그때 enum/코드 테이블 여부를 다시 판단한다. |
| `jobCategory` | `String` (nullable) | 아니오 | 직무/직군(예: "IT/전산", "AX", "경영지원"). 위와 동일한 이유로 자유 문자열. |
| `location` | `String` (nullable) | 아니오 | 근무 지역. 구조화된 지역 코드 대신 자유 문자열(수집 전이라 실제 표기 형태를 모름). |
| `applicationStartAt` | `LocalDate` (nullable) | 아니오 | 접수 시작일. 상시채용/수시채용 등 시작일이 없는 공고가 존재할 수 있어 nullable. 시각(시:분)까지는 이번 MVP에서 다루지 않고 날짜 단위로 충분하다고 판단(대부분의 채용 공고가 날짜 단위로 마감을 표기). |
| `applicationEndAt` | `LocalDate` (nullable) | 아니오 | 접수 마감일. 이유는 `applicationStartAt`과 동일. 향후 "마감 임박 알림" 기능의 핵심 필드가 될 것이므로 개념 자체는 반드시 포함하되, 이번 Task에서는 그 계산 로직을 만들지 않는다(Out of Scope). |
| `source` | `String` | **필수** | 원본 출처 식별자(자유 문자열. 예: `"MANUAL"`, 향후 `"ALIO"`, `"COMPANY_SITE"` 등). Crawling Source별 클래스/enum을 만들지 않고 단순 문자열로 최소 표현만 한다. 데이터가 어디서 왔는지는 처음부터 필수로 강제해, 나중에 "출처를 모르는 레코드"가 쌓이는 것을 막는다. |
| `sourceUrl` | `String` (nullable) | 아니오 | 원본 공고 URL. 수동 생성 데이터 등에는 없을 수 있어 nullable. 값이 있으면 `@URL` 형식 검증(Hibernate Validator 내장 기능, 신규 dependency 아님)을 적용한다. |
| `externalId` | `String` (nullable) | 아니오 | 외부 시스템 식별자. 지금은 중복 제거 로직이 없으므로 단순 보관 필드. Unique 제약은 걸지 않는다(Out of Scope: 중복 제거). |
| `createdAt` | `Instant` | (자동 생성) | CareerOps 저장 시각. `@CreationTimestamp`(Hibernate 제공 애노테이션, 추가 dependency 아님)로 엔티티 생성 시 자동 기록. `BaseEntity`를 만들지 않고 `JobPosting`에 필드 하나로 직접 선언한다. |

**Company를 별도 Entity로 분리하지 않는 이유**: 지금은 회사별로 공고를
묶어 조회/검색하는 기능(Out of Scope), 회사 프로필/메타데이터를 저장할
필요, 여러 소스에서 온 동일 회사명을 정규화(dedup)할 필요가 전혀 없다.
지금 `Company` Entity를 만들면 실제 데이터 없이 정규화 규칙(회사명 표기
통일 방식 등)을 추측하게 되어 "MVP에서 과도한 정규화 금지" 원칙에
위배된다. 여러 실제 소스가 붙어 회사명 중복/표기 차이가 실제 문제로
드러나면 그때 `Company` Entity 도입을 별도 Task로 설계한다.

### 2. 패키지/클래스 구조

CORE-001은 `domain/service/repository/controller` 같은 계층형 최상위
패키지를 만들지 않기로 했다(도메인이 없었으므로). 이제 첫 도메인이
생기지만, 여전히 도메인이 1개뿐인 시점에 계층형 최상위 패키지
(`com.careerops.backend.controller`, `.service`, `.repository`,
`.domain` 등)로 흩어 놓는 것보다, 기능 단위(feature-package)로 묶는 것이
탐색하기 쉽고 향후 다른 도메인(PKB, Matching 등)이 추가될 때도 서로
섞이지 않는다. 따라서 아래처럼 `job` 패키지 하나에 이 기능의 전부를
둔다.

```
backend/src/main/java/com/careerops/backend/
└── job/
    ├── JobPosting.java              # @Entity
    ├── JobPostingRepository.java    # interface extends JpaRepository<JobPosting, Long>
    ├── JobPostingService.java       # 단일 클래스(인터페이스 없음, 이유는 Out of Scope 참고)
    ├── JobPostingController.java    # @RestController, "/api/jobs"
    └── dto/
        ├── JobPostingCreateRequest.java   # record, Bean Validation 애노테이션 포함
        └── JobPostingResponse.java        # record

backend/src/main/resources/db/migration/
└── V1__create_job_postings_table.sql      # Flyway migration (Codex가 작성)

backend/src/test/java/com/careerops/backend/job/
├── JobPostingRepositoryTest.java
└── JobPostingControllerTest.java
```

### 3. DTO ↔ Entity 분리 방식

- `JobPostingCreateRequest`(record): 클라이언트가 보내는 필드만 포함
  (`companyName`, `title`, `employmentType`, `jobCategory`, `location`,
  `applicationStartAt`, `applicationEndAt`, `source`, `sourceUrl`,
  `externalId`). `id`, `createdAt`은 서버가 생성하므로 포함하지 않는다.
  Bean Validation 애노테이션(`@NotBlank`, `@Size`, `@URL` 등)을 record
  컴포넌트에 직접 붙인다(Java 21 record는 Bean Validation을 컴포넌트
  단위로 지원하며 Lombok 없이 불변 DTO를 만드는 방법으로 충분하다).
- `JobPostingResponse`(record): `id`, `companyName`, `title`,
  `employmentType`, `jobCategory`, `location`, `applicationStartAt`,
  `applicationEndAt`, `source`, `sourceUrl`, `externalId`, `createdAt`
  전체를 포함. `JobPostingService` 또는 Controller에서 `JobPosting`
  엔티티로부터 정적 팩토리 메서드(예: `JobPostingResponse.from(JobPosting)`)로
  변환한다. Entity를 API 응답에 직접 노출하지 않는다.
- `JobPosting` 엔티티는 record가 아닌 일반 클래스로 만든다(JPA 엔티티는
  프록시/지연 로딩/no-arg 생성자 요구사항 때문에 record로 만들 수 없다).
  Setter는 최소화하고(필드 접근 전략 `@Access(AccessType.FIELD)`가 기본
  동작이 되도록 `@Id`를 필드에 선언), 생성은 비즈니스 생성자(필수/선택
  필드를 받는) + protected no-arg 생성자(JPA 요구사항)로 처리한다. 이번
  Task에는 수정(PUT/PATCH) API가 없으므로 setter가 사실상 필요 없다.

### 4. DB Migration 전략 — Flyway 채택

`docs/DECISIONS.md` **ADR-0006**에 근거를 기록했다. 요약: Hibernate
`ddl-auto=update`(또는 `create`류) 대신 **Flyway**로 스키마를 버전
관리한다. `spring.jpa.hibernate.ddl-auto`는 `validate`로 설정해 Hibernate가
스스로 스키마를 바꾸지 않고, entity 매핑과 실제 스키마가 어긋나면 기동
자체가 실패하도록 한다(조기 오류 탐지).

- 마이그레이션 파일: `backend/src/main/resources/db/migration/V1__create_job_postings_table.sql`.
  Flyway 기본 네이밍 컨벤션(`V{version}__{description}.sql`)을 따른다.
  이 SQL 파일은 이번 호출(architect)에서 작성하지 않는다 — Codex 구현
  범위다.
- 테이블명: `job_postings`(snake_case, 복수형 — Spring Data JPA/Hibernate
  기본 네이밍 전략과 자연스럽게 매칭).
- PK는 Postgres identity 컬럼(`GENERATED BY DEFAULT AS IDENTITY` 또는
  동등한 방식)으로 만들고, 엔티티의 `@GeneratedValue(strategy = GenerationType.IDENTITY)`와
  맞춘다.
- `source` + `externalId` 조합에 unique 제약은 걸지 않는다(중복 제거는
  Out of Scope).

| `org.springframework.boot:spring-boot-starter-webmvc-test` (test) | **구현 중 발견해 추가 승인.** 같은 이유로 `@AutoConfigureMockMvc`가 `spring-boot-webmvc-test`로 분리됐다(`org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc`). `spring-boot-starter-webmvc-test`가 이를 포함한 스타터다. |

두 추가 모두 **test scope**이며 Technical Notes 작성 시점(3.x식 단일 test-autoconfigure 모듈을 전제)의 계획 오류를 바로잡는 것이지, 새 기능이나 프로덕션 의존성이 아니다. Codex가 `./gradlew compileTestJava`에서 `DataJpaTest`/`AutoConfigureTestDatabase`/`AutoConfigureMockMvc` 클래스를 찾을 수 없다는 실제 컴파일 에러로 이를 먼저 발견했고, 임의로 추측 추가하지 않고 블로커로 보고했다(올바른 대응). Claude가 Maven Central에서 4.1.0 jar 내용을 직접 검사해 정확한 대체 artifact를 확인한 뒤 승인했다.

| `org.springframework.boot:spring-boot-starter-flyway` | **구현 중 발견해 추가 승인 (2차 블로커).** Spring Boot 3.x까지는 `flyway-core`가 클래스패스에 있으면 `spring-boot-autoconfigure`가 Flyway를 자동 구성했다. Boot 4.1은 이 자동구성을 `spring-boot-autoconfigure`에서 떼어내 별도 모듈 `spring-boot-flyway`로 분리했고(`spring-boot-autoconfigure-4.1.0.jar`에 Flyway 클래스가 전혀 없음을 jar 직접 검사로 확인), 이를 클래스패스에 올리는 공식 경로가 `spring-boot-starter-flyway`다(이 starter가 `spring-boot-flyway` + `flyway-core`를 함께 가져온다). 이 starter가 `flyway-core`를 transitively 포함하므로, 기존에 명시했던 `implementation 'org.flywaydb:flyway-core'` 줄은 중복이 되어 제거한다. `flyway-database-postgresql`은 `spring-boot-flyway`가 가져오지 않으므로 계속 명시적으로 둔다. |

이 역시 ADR-0006에서 이미 승인된 "Flyway로 스키마 관리" 결정을 Boot 4.1에서 실제로 동작시키기 위한 배관 수정이지, 새로운 아키텍처 결정이 아니다. Codex가 Hibernate `Schema validation: missing table [job_postings]` 실패(Flyway 마이그레이션이 전혀 실행되지 않음)로 이를 발견하고 추측으로 넘어가지 않고 다시 블로커로 보고했다.

버전은 명시하지 않는다 — `build.gradle`의 `io.spring.dependency-management`
플러그인(Spring Boot BOM)이 Spring Boot 4.1.x와 호환되는 버전을 관리한다
(CORE-001과 동일한 방식).

**추가하지 않는 것과 이유**:
- **Lombok**: 이번 Task는 Entity 1개, DTO 2개(record)뿐이라 보일러플레이트
  비용이 낮다. DTO는 record로 이미 Lombok 없이 불변/간결하게 표현되고,
  Entity는 setter를 사실상 두지 않으므로 `@Getter`/`@Builder` 없이도
  관리 가능한 수준이다. 프로젝트 전체 기본값("추가 안 해도 되면 안
  하는 게 기본값")을 유지한다. Entity/DTO 수가 늘어나 반복 비용이 실제로
  체감되는 시점(다음 도메인 1~2개 추가 이후)에 재검토한다.
- **MapStruct**: 매핑 방향이 Entity→Response 하나뿐이고 필드 수가
  10여 개 수준이라, 정적 팩토리 메서드 하나로 충분하다. 매핑 로직이
  여러 Entity/DTO 쌍으로 늘어나 반복이 실제 문제가 될 때 재검토한다.
- **Testcontainers**: CORE-001에서 이미 "로컬 Docker Compose PostgreSQL을
  테스트 사전조건으로 사용" 방식을 확립했고, `ddl-auto=validate` +
  Flyway 조합이 실제 PostgreSQL 방언에서 정상 동작하는지도 이 로컬
  Postgres로 검증된다. CI가 아직 없는 1인 프로젝트 단계에서 Testcontainers를
  들이는 것은 선제적 확장이다. CI 파이프라인을 실제로 구성하는 시점에
  재검토한다(그때는 CI 환경에 상시 Postgres가 없을 수 있으므로 근거가
  달라진다).

### 6. Product Metric 정의 및 Micrometer 연동

`docs/METRICS.md`의 "Product Metrics" 섹션에 동일 내용을 반영했다.

**이름 정정 (구현 중 발견, 3차 블로커):** 최초 계획은 Micrometer 이름
`careerops.job.created`(Prometheus 노출명 `careerops_job_created_total`)였다.
Codex가 실제로 `/actuator/prometheus`를 curl한 결과 `careerops_job_total`로
잘못 노출되는 것을 발견했다 — Micrometer의 Prometheus 네이밍 컨벤션이
`created`/`total`/`count`/`sum`/`bucket` 등 OpenMetrics/Prometheus 예약
접미사와 겹치는 마지막 단어를 이름에서 제거한 뒤 자체 접미사(`_total` 등)를
붙이기 때문이다(라이브러리의 의도된 동작이며 버그가 아니다). `read` 카운터는
예약어와 겹치지 않아 `careerops_job_read_total`로 정상 노출됐다. 이를 피하기
위해 Micrometer 이름을 `careerops.job.creation`으로 변경했다(Prometheus 노출명
`careerops_job_creation_total`). Acceptance Criteria와 Scope의 metric 이름도
이에 맞춰 갱신했다.

| Micrometer 이름 | Prometheus 노출명 | 타입 | 태그 | 의미 | 계측 위치 |
|---|---|---|---|---|---|
| `careerops.job.creation` | `careerops_job_creation_total` | Counter | 없음 | `JobPosting`이 성공적으로 저장된 누적 횟수 | `JobPostingService.create()` — 저장 성공 직후 1 증가 |
| `careerops.job.read` | `careerops_job_read_total` | Counter | `result` = `found` \| `not_found` | `GET /api/jobs/{id}` 조회 결과 분포. `not_found`가 비정상적으로 높으면 깨진 링크/오동작 신호로 활용 가능 | `JobPostingService.findById()` — 조회 결과가 결정된 직후 1 증가 |

- `MeterRegistry`는 CORE-001에서 이미 클래스패스에 있는
  `micrometer-registry-prometheus`(+ Actuator 자동 구성)를 통해 Spring
  컨텍스트에 Bean으로 존재한다. **신규 dependency 불필요** — 확인 완료.
  `JobPostingService`에 생성자로 `MeterRegistry`를 주입받아
  `Counter.builder("careerops.job.creation").register(meterRegistry).increment()`,
  `Counter.builder("careerops.job.read").tag("result", "found"|"not_found").register(meterRegistry).increment()`
  형태로 사용한다.
- 커스텀 `MeterBinder`나 별도 Metrics 설정 클래스는 만들지 않는다 —
  카운터 2개 등록/증가만으로 충분한 규모다.
- `source` 필드 값으로 태깅하지 않는다 — `source`는 지금 자유 문자열
  입력값이라 Prometheus label cardinality가 무한정 늘어날 위험이 있다
  (예: 오타/임의 문자열이 그대로 label이 됨). 소스가 실제로 고정된 값
  집합으로 정리되는 시점(예: enum화)에 재검토한다.
