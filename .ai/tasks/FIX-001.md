## Context

PKB-002/003/004(Certification/Education/Award CRUD, migration V8~V10)까지
완료되어 전체 테스트 125/125 PASS 상태였다. 그러나 실제 dev API 회귀 검증
과정에서 PKB-001부터 존재하던 `CareerExperience` 목록 조회 버그가 발견됐다:
`GET /api/career/experiences`를 `keyword` 파라미터 없이 호출하면 HTTP 500이
발생한다(`type` 유무와 무관).

### 재현 결과 (Claude가 실제 dev/test 양쪽 Postgres에 `bootRun`으로 확인)

| 요청 | 결과 |
|---|---|
| `GET /api/career/experiences` (파라미터 없음) | **500** |
| `GET /api/career/experiences?type=PROJECT` (keyword 없음) | **500** |
| `GET /api/career/experiences?keyword=spring` (type 없음) | 200 |
| `GET /api/career/experiences?type=PROJECT&keyword=spring` | 200 |
| `GET /api/career/experiences?keyword=` (빈 문자열) | 200 (모든 title에 매치, blank trim 없음) |
| `GET /api/career/experiences?keyword=%20` (공백) | 200 (공백 literal로 LIKE, blank trim 없음) |

→ **`keyword`가 null일 때만** 실패한다. non-null 문자열(빈 문자열/공백 포함)은
성공한다.

### Root cause

현재 JPQL(`CareerExperienceRepository.search`):

```sql
WHERE (:type IS NULL OR e.type = :type)
  AND (:keyword IS NULL OR LOWER(e.title) LIKE LOWER(CONCAT('%', :keyword, '%')))
```

`:keyword`는 실제 실행 SQL에서 서로 다른 두 개의 `?`로 바인딩된다
(`? is null` 체크용 하나, `lower(('%'||?||'%'))` 안에서 쓰이는 것 하나). 후자는
엔티티의 매핑된 컬럼과 직접 비교되지 않고 `CONCAT` 함수 인자 위치에서만
등장하므로, Hibernate(7.4.1)가 이 파라미터의 JDBC 타입을 컨텍스트로부터
추론하지 못한다. 값이 null인 경우 Hibernate가 타입을 명시적으로 지정하지
못해(non-null 문자열은 `setString()`으로 명시 타입 지정되어 문제없음) 결과적으로
pgjdbc가 bytea OID로 파라미터를 선언 → Postgres가 `lower(bytea)` 오버로드를
찾지 못해 `ERROR: function lower(bytea) does not exist` 발생.

### 기존 테스트가 못 잡은 이유

`CareerExperienceControllerTest`는 전부 `@Transactional` + `@Rollback`으로
감싸져 있다. Claude가 실제 `bootRun`(실 HTTP 서버, 트랜잭션 미리 열지 않음 —
`CareerExperienceService.findAll()`은 `@Transactional`이 없고 open-in-view로
처리됨)과 `@Transactional` MockMvc 테스트 양쪽으로 동일한 keyword=null 요청을
비교 실행한 결과, **`@Transactional`로 감싼 테스트 경로에서는 이 버그가
재현되지 않고, 실제 요청 경로에서만 재현됨**을 확인했다. 즉 "keyword 없이
호출하는 테스트가 없어서"가 아니다 — 기존 `listsWithCombinedFiltersAsFlatResponses`
테스트도 `.param("type","WORK")`만 넘겨 keyword=null인 케이스를 이미 실행하고
있었지만 통과했다. **테스트가 실제 요청과 다른 트랜잭션 경계를 사용해서** 이
버그를 못 잡았다. 따라서 이번에 추가하는 회귀 테스트는 `@Transactional`로
감싸지 않아야 한다(아래 Technical Notes 참고).

## Scope

`GET /api/career/experiences`가 `keyword` 파라미터 유무와 관계없이 항상 200을
반환하도록 `CareerExperienceRepository.search()`의 null-parameter typing
문제를 제거한다.

### 채택한 수정 방식

JOB-002(`JobPostingRepository.search` + `JobPostingService.likePattern()`)
선례를 따른다 — Java 쪽에서 `%value%` 패턴을 미리 만들어 `LIKE :param`으로
**직접**(함수 인자 위치가 아니라 LIKE의 피연산자로) 바인딩한다. JOB-002는
대소문자 무시가 필요 없어 `LOWER()`가 없었지만, CareerExperience는 대소문자
무시가 필요하므로 Java에서 미리 lowercase까지 적용한 패턴을 만들어 전달하고,
JPQL은 `LOWER(e.title) LIKE :keywordPattern`으로 비교한다(파라미터가 LIKE
우변에 직접 위치 — Hibernate가 `LOWER()`의 등록된 반환 타입(String)으로 정상
추론).

**변경 파일 (Claude가 사전 검증 완료, 정확히 이 diff를 적용):**

`backend/src/main/java/com/careerops/backend/career/CareerExperienceRepository.java`
```diff
         WHERE (:type IS NULL OR e.type = :type)
-          AND (:keyword IS NULL OR LOWER(e.title) LIKE LOWER(CONCAT('%', :keyword, '%')))
+          AND (:keywordPattern IS NULL OR LOWER(e.title) LIKE :keywordPattern)
         ORDER BY e.updatedAt DESC
         """)
     Page<CareerExperienceResponse> search(@Param("type") ExperienceType type,
-                                          @Param("keyword") String keyword, Pageable pageable);
+                                          @Param("keywordPattern") String keywordPattern, Pageable pageable);
```

`backend/src/main/java/com/careerops/backend/career/CareerExperienceService.java`
```diff
     public CareerExperienceListResponse findAll(ExperienceType type, String keyword, Pageable pageable) {
         int size = Math.min(pageable.getPageSize(), 100);
-        return CareerExperienceListResponse.from(repository.search(type, keyword, PageRequest.of(pageable.getPageNumber(), size)));
+        return CareerExperienceListResponse.from(repository.search(type, keywordPattern(keyword), PageRequest.of(pageable.getPageNumber(), size)));
+    }
+
+    private static String keywordPattern(String keyword) {
+        return keyword == null ? null : "%" + keyword.toLowerCase(Locale.ROOT) + "%";
     }
```

(`java.util.*`가 이미 import되어 있어 `Locale` 추가 import 불필요.)

Claude가 이 diff를 실제로 적용해 dev DB(`careerops`)와 test DB
(`careerops_test`) 양쪽에 `bootRun`으로 띄운 실제 서버에서 검증 완료:
무파라미터/type only/keyword only/둘다/빈 문자열/공백/대소문자 무시("SPRING"

└── CareerExperienceControllerTest.java (또는 신규 테스트 클래스)

### 왜 `@Transactional` 테스트만으로는 부족한가

기존 `CareerExperienceControllerTest`는 클래스 레벨 `@Transactional` +
`@Rollback`이다. Claude의 재현 실험 결과 이 경로에서는 keyword=null 버그가
재현되지 않았다(Spring이 트랜잭션을 미리 열고 커넥션을 관리하는 경로에서
Hibernate/pgjdbc의 파라미터 바인딩 동작이 실제 무-트랜잭션 HTTP 요청 경로와
달라짐). 따라서 이번 회귀 테스트는 다음 중 하나로 작성한다:

1. `@Transactional`이 없는 별도 `@SpringBootTest` + `@AutoConfigureMockMvc`
   테스트 클래스를 신설하고, 테스트가 만든 데이터는 `@AfterEach`에서 직접
   삭제해 격리한다(rollback에 의존하지 않음). **권장.**
2. 또는 실제 임베디드 서버 포트로 뜬 인스턴스에 `TestRestTemplate`/`RestClient`로
   실제 HTTP 요청을 보내는 통합 테스트(`@SpringBootTest(webEnvironment =
   RANDOM_PORT)`).

`@DataJpaTest` 기반 `CareerExperienceRepositoryTest`(`AutoConfigureTestDatabase.Replace.NONE`)
에 `repository.search(...)`를 직접 호출하는 테스트를 추가하는 것도 유효하지만,
이 경로도 트랜잭션 안에서 실행되므로 컨트롤러 레벨의 비-트랜잭션 테스트를
반드시 최소 1개 포함해야 한다(위 Acceptance Criteria 참고).

### 참고 — JOB-002 선례

`JobPostingRepository.search()` / `JobPostingService.likePattern()`
(`backend/src/main/java/com/careerops/backend/job/`)이 동일한 `(:param IS NULL
OR column LIKE :param)` 패턴을 Java에서 미리 만든 `%value%` 문자열로 해결한
선례다. 이번 수정은 그 패턴에 `LOWER()`만 추가한 것이다.
