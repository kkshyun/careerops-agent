## Context

APPLICATION-001로 `JobApplication`(지원 전체 상태: INTERESTED/PLANNED/
SUBMITTED/OFFERED/REJECTED/WITHDRAWN)까지는 관리할 수 있게 됐지만, 실제
채용 전형은 서류/코딩테스트/필기/면접/최종 등 여러 단계로 나뉘고 각 단계마다
별도의 일정과 결과가 있다. ADR-0016에서 이미 "`status`는 지원 전체
국면만 표현하고, 전형 단계별 일정/결과는 별도 모델(`ApplicationStage`)로
분리한다"고 설계해뒀다 — 이번 Task가 그 `ApplicationStage`를 실제로
만든다.

Calendar/알림/AI 기능, ALIO `RecruitmentStep`(외부 원본 데이터)과의 연동은
이번 Phase에서 다루지 않는다. `ApplicationStage`는 사용자가 자신의 지원
과정을 관리하기 위해 직접 만드는 데이터이고, `RecruitmentStep`은 ALIO가
제공한 공고 원본 메타데이터로 서로 다른 개념이다 — 자동 변환/연결하지 않는다.

## Scope

`ApplicationStage` entity 신설 + `JobApplication` 하위 리소스 CRUD API.

### 1. Entity — `com.careerops.backend.application.ApplicationStage`

```java
@Entity
@Table(name = "application_stages")
public class ApplicationStage {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;

    @ManyToOne(optional = false, fetch = FetchType.LAZY)
    @JoinColumn(name = "job_application_id", nullable = false)
    private JobApplication jobApplication;

    @Enumerated(EnumType.STRING)
    @Column(name = "stage_type", nullable = false, length = 50)
    private StageType stageType;

    @Column(length = 100)
    private String label;

    @Column(name = "sort_order", nullable = false)
    private Integer sortOrder;

    @Column(name = "scheduled_at")
    private LocalDateTime scheduledAt;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 50)
    private StageResult result;

    @Column(length = 1000)
    private String memo;

    @CreationTimestamp private Instant createdAt;
    @UpdateTimestamp private Instant updatedAt;
    ...
}
```

`JobApplication`(`application.JobApplication`)의 `@ManyToOne(optional =
false, fetch = FetchType.LAZY) @JoinColumn` 패턴을 그대로 재사용한다.
`JobApplication` 쪽에는 `ApplicationStage`에 대한 역참조 컬렉션
(`@OneToMany`)을 추가하지 않는다 — `RecruitmentStep`/`Attachment`가
`JobPosting`을 역참조하지 않는 기존 패턴과 동일(단방향 `@ManyToOne`만).

`scheduledAt`은 `LocalDateTime`(시간 포함, timezone 미도입 — 프로젝트
전체가 단일 서버/단일 사용자 전제라 wall-clock 그대로 저장하고 별도 zone
변환 로직을 만들지 않는다).

### 2. `StageType` enum (신규, `EnumType.STRING`)

```java
public enum StageType {
    DOCUMENT,      // 서류전형
    CODING_TEST,   // 코딩테스트
    WRITTEN,       // 필기(NCS/전공/인적성 등 코딩테스트 외 필기성 전형)
    INTERVIEW,     // 면접(1차/2차/실무/임원 등은 label로 구분)
    FINAL,         // 최종 합격/처우협의
    OTHER          // 위에 속하지 않는 특수 전형(AI면접/신체검사/신원조회 등)
}
```

같은 `stageType`이 한 `JobApplication` 안에 여러 번 나타날 수 있다(예:
INTERVIEW 1차/2차) — DB/애플리케이션 어디에도 `stageType` 단독 유일성
제약을 두지 않는다. `label`(nullable)로 "1차 면접"/"2차 면접"처럼 사용자가
같은 타입의 단계를 구분한다.

### 3. `StageResult` enum (신규, `EnumType.STRING`, not null)

```java
public enum StageResult {
    PENDING,    // 아직 결과 없음 (기본값)
    PASSED,
    FAILED,
    CANCELLED
}
```

생성 시 `result`를 생략하면 서비스가 `PENDING`으로 기본값을 설정한다(컬럼은
`NOT NULL` — `JobApplication.status`와 동일하게 "미정" 자체를 명시적인 enum
값으로 표현). `JobApplication.status`(OFFERED/REJECTED 등, 지원 전체 국면)와
`ApplicationStage.result`(개별 전형 단계의 합/불)는 서로 다른 축이다 —
어느 쪽도 다른 쪽을 자동으로 파생/변경하지 않는다(아래 6번).

### 4. Migration — `V6__create_application_stages_table.sql`

```sql
CREATE TABLE application_stages (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    job_application_id BIGINT NOT NULL REFERENCES job_applications(id) ON DELETE CASCADE,
    stage_type VARCHAR(50) NOT NULL,
    label VARCHAR(100),
    sort_order INTEGER NOT NULL,
    scheduled_at TIMESTAMP(6),
    result VARCHAR(50) NOT NULL,
    memo VARCHAR(1000),
    created_at TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    updated_at TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    CONSTRAINT uk_application_stages_application_sort_order UNIQUE (job_application_id, sort_order)
);
```

`job_application_id` FK는 **`ON DELETE CASCADE`**(ADR-0017 — `JobPosting`→
`JobApplication`의 NO ACTION 컨벤션을 그대로 복제하지 않고, `ApplicationStage`는
`JobApplication` 없이는 독립적 의미가 없는 진짜 aggregate 내부 데이터라는
점에 근거해 다르게 결정). `stage_type` 단독 index는 추가하지 않는다 —
`UNIQUE(job_application_id, sort_order)`가 `job_application_id` 선두 컬럼
조회도 함께 지원한다.

### 5. 중복/유일성 정책 — `sortOrder` 자동 할당 + DB UNIQUE

- 같은 `jobApplicationId` 안에서 `sortOrder`는 유일해야 한다(위 migration).
- 생성 요청에서 `sortOrder`를 생략하면 서비스가 그 `JobApplication`의 현재
  최대 `sortOrder` + 1(없으면 1)을 자동 할당한다.
- 명시적으로 `sortOrder`를 지정했는데 이미 사용 중이면 DB UNIQUE 위반
  (`DataIntegrityViolationException`)을 catch해 **409 Conflict**로 변환한다
  (APPLICATION-001의 `jobPostingId` 중복 처리와 동일한 catch 패턴, `JobApplicationService.create()`
  참고).
- `stageType` 반복에는 어떤 제약도 두지 않는다(위 2번).

### 6. `JobApplication.status` 자동 변경 없음

`ApplicationStage.result`가 어떻게 바뀌어도 `JobApplication.status`를
서비스가 자동으로 전이시키지 않는다(예: FINAL 단계가 PASSED가 되어도
`status`를 자동으로 OFFERED로 바꾸지 않음). 두 필드 모두 사용자가 각각
명시적으로 관리한다. 어떤 이벤트 리스너/훅도 만들지 않는다.

### 7. API — `JobApplication`의 nested resource

신규 `ApplicationStageController`(같은 `application` 패키지):

```
POST   /api/applications/{applicationId}/stages       -> 201, ApplicationStageResponse
GET    /api/applications/{applicationId}/stages        -> 200, List<ApplicationStageResponse> (sortOrder ASC)
GET    /api/applications/{applicationId}/stages/{id}   -> 200, ApplicationStageResponse / 404
PATCH  /api/applications/{applicationId}/stages/{id}   -> 200, ApplicationStageResponse / 404
DELETE /api/applications/{applicationId}/stages/{id}   -> 204 / 404
```

모든 엔드포인트는 먼저 `applicationId`에 해당하는 `JobApplication`이
존재하는지 확인한다(없으면 404). 단건 조회/PATCH/DELETE는 추가로 그
`id`의 `ApplicationStage`가 실제로 그 `applicationId`에 속하는지 확인한다
(다른 application 소속이면 404 — `ApplicationStageRepository.findByIdAndJobApplicationId(...)`).

**`POST .../stages`** — Request `ApplicationStageCreateRequest`:
```json
{ "stageType": "INTERVIEW", "label": "1차 면접", "sortOrder": 3,
  "scheduledAt": "2026-09-03T14:00:00", "result": null, "memo": "온라인 진행" }
```
- `stageType`: `@NotNull`.
- `label`/`sortOrder`/`scheduledAt`/`result`/`memo`: 전부 optional.
  `sortOrder` 생략 시 자동 할당(5번), `result` 생략 시 `PENDING` 기본값.

**`PATCH .../stages/{id}`** — Request `ApplicationStageUpdateRequest`
(`label`/`scheduledAt`/`result`/`memo`/`sortOrder` 수정 가능, `stageType`은
수정 불가 — 잘못 만들었으면 삭제 후 재생성). APPLICATION-001의 PATCH
컨벤션과 동일하게 **필드가 없거나 JSON `null`이면 무변경**이다(부분 수정,
PUT 아님). `result`는 `PENDING`이 실제 enum 상수(자바 `null`이 아님)이므로
이 무변경 규칙과 충돌하지 않는다 — 요청에서 `result` 필드를 생략하거나
JSON `null`을 보내면 무변경이고, `{"result":"PENDING"}`처럼 **명시적으로
`PENDING` 값을 보내면 실제로 그 값으로 변경된다**. 즉 한 번 `PASSED`/
`FAILED`로 정한 `result`를 다시 `PENDING`(결과 미정)으로 되돌리는 것은
**이 PATCH로 이미 가능하다** — `PENDING`을 진짜 enum 값으로 둔 설계
의도(4번) 그대로다. `memo`/`label` 등 String 필드는 "생략=무변경"과
"빈 문자열로 지우기"가 여전히 구분되지 않는 한계가 남아있지만(JSON
Merge Patch 등 별도 표준은 도입하지 않음 — Out of Scope), 이는 `result`
(nullable이 아닌 enum이라 "미정" 자체가 값으로 존재)와는 다른 케이스다.

**응답 DTO — `ApplicationStageResponse`**:
```json
{ "id": 10, "stageType": "INTERVIEW", "label": "1차 면접", "sortOrder": 3,
  "scheduledAt": "2026-09-03T14:00:00", "result": "PENDING",
  "memo": "온라인 진행", "createdAt": "...", "updatedAt": "..." }
```
`jobApplicationId`는 응답에 포함하지 않는다(경로에 이미 있음, JOB-003의
`RecruitmentStepResponse`/`AttachmentResponse`가 부모 id를 응답에 넣지 않는
것과 동일 원칙). `JobPostingDetailResponse.from(entity)` 패턴을 참고해
`ApplicationStageResponse.from(ApplicationStage entity)` 정적 팩토리로
매핑한다(cross-entity JOIN이 필요 없으므로 JPQL constructor expression이
아니라 entity → record 직접 매핑, `RecruitmentStepResponse.from(...)`와
동일 패턴).

### 8. `GET /api/applications/{id}` 상세 응답에 `stages` 포함

JOB-003의 `JobPostingDetailResponse` 패턴을 그대로 재사용한다 — 신규
`JobApplicationDetailResponse`(기존 `JobApplicationResponse`의 모든 필드 +
`List<ApplicationStageResponse> stages`, `sortOrder ASC` 정렬)를 만들고,
`JobApplicationController.findById()`가 지금의 `JobApplicationResponse`
대신 이걸 반환하도록 바꾼다. `JobApplicationService.findById()`를
`JobApplicationRepository.findResponseById()`(기존 JOIN 쿼리, 무변경) +
`ApplicationStageRepository.findByJobApplicationIdOrderBySortOrderAsc(id)`
(신규 derived query, 자식 1건 조회) 2-query 조합으로 확장한다.

**`GET /api/applications`(목록)와 `POST`/`PATCH /api/applications`(생성/수정)
응답은 변경하지 않는다** — 기존 `JobApplicationResponse`(stages 없음) 그대로
반환한다. 목록 API에서 application마다 stage 쿼리를 추가로 날리는 N+1을
만들지 않는다.

### 9. Transaction boundary

`@Transactional`을 추가하지 않는다. `JobApplicationService`(ADR-0015)와
동일한 근거 — Stage CRUD 각각이 read 여러 번 뒤 단일 write 하나로 끝나고,
`sortOrder` race는 DB UNIQUE 제약이 최종적으로 막는다(5번).

## Out of Scope

- Calendar UI/Google Calendar 연동, D-7/D-3/D-1 일정 알림.
- `JobApplication.status` 자동 전이(6번 참고 — 만들지 않음).
- ALIO `RecruitmentStep` → `ApplicationStage` 자동 생성/연결.
- 단계 순서 일괄 재정렬 API(예: 여러 stage의 `sortOrder`를 한 요청으로 교체).
  이번 Phase는 PATCH로 단일 stage의 `sortOrder` 개별 수정만 지원.
- JSON Merge Patch류 표준 도입(String 필드를 "생략=무변경"과 "빈 값으로
  지우기"로 구분하는 것은 여전히 범위 밖 — 단, `result`를 `PENDING`으로
  되돌리는 것 자체는 Out of Scope가 아니다. `PENDING`이 실제 enum 값이라
  이미 지원됨, 7번 참고).
- 사용자 인증/다중 사용자, PKB, 공고-경험 matching, 자기소개서 Agent, Frontend.
- 수집 인프라 개선, ALIO detail resync, 분산 락.
- custom Prometheus metric — 일반 CRUD라 기존 Spring HTTP metric으로 충분.

## Technical Notes

- 기존 `job`/`collector` 패키지는 이번 Task에서 수정하지 않는다.
- `JobApplicationController.findById()`/`JobApplicationService.findById()`의
  반환 타입이 `JobApplicationResponse` → `JobApplicationDetailResponse`로
  바뀐다 — 이 변경이 기존 `JobApplicationControllerTest`의 단건 조회
  관련 테스트(`jsonPath` assertion)에 영향을 주는지 확인하고, 영향이 있으면
  그 테스트도 함께 갱신한다(기존 필드는 전부 그대로 유지되고 `stages`
  필드만 추가되므로 fields 자체의 회귀는 없어야 한다).
- 테스트는 기존 컨벤션을 그대로 따른다 — `careerops_test` DB(자동 격리),
  `@SpringBootTest` + `@AutoConfigureMockMvc` + `@Transactional` + `@Rollback`
  (`JobApplicationControllerTest` 패턴 참고).
- N+1 회귀 확인은 `spring.jpa.properties.hibernate.generate_statistics`
  같은 신규 설정을 추가하지 않고, 목록 조회 시 `ApplicationStageRepository`
  관련 쿼리가 아예 호출되지 않는다는 사실(코드 경로상 `search()`가
  `ApplicationStageRepository`를 참조하지 않음)로 검증해도 된다 —
  과도한 계측 도입 금지 원칙.
- 신규 production/test dependency 없음.
