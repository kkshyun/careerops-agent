clean main HEAD에서 `ImportCandidateConcurrencyTest`를 35회(15+20)
반복 실행한 결과 22회(약 63%) 실패했다. 실패는 **항상**
`concurrentCompleteAndCreatePreserveBatchInvariant()`에서만 발생했다
(`concurrentApproveCreatesExactlyOnePkbRow()`는 35회 전부 통과).

```
org.opentest4j.AssertionFailedError: Expecting value to be false but was true
  at ImportCandidateConcurrencyTest.concurrentCompleteAndCreatePreserveBatchInvariant(ImportCandidateConcurrencyTest.java:84)
```

`completeSuccess.get() == 1` 분기에서 `assertThat(pending).isFalse()`가
실패 — `batchService.complete()`가 200을 반환했는데 같은 batch에
`PENDING` candidate가 실제로 존재하는 상태.

**애플리케이션/Hibernate를 완전히 배제하고 raw SQL 두 세션으로 직접
재현**했다: 세션 A가 `SELECT ... FOR UPDATE`로 `import_batches` row를
잠근 뒤 `import_candidates`에 `PENDING` row INSERT 후 COMMIT, 세션 B는
A가 lock을 쥔 동안 `UPDATE import_batches SET status='COMPLETED', ...
WHERE status='OPEN' AND NOT EXISTS (SELECT 1 FROM import_candidates
WHERE status='PENDING') ...`를 실행해 A의 lock을 기다렸다. A가 커밋한
뒤 B의 UPDATE가 unblock됐을 때, **B는 여전히 성공해서 batch를
COMPLETED로 만들었다** — A가 방금 커밋한 PENDING candidate가 존재하는데도.

이는 애플리케이션 버그가 아니라 **PostgreSQL READ COMMITTED의 문서화된
caveat**이다: UPDATE가 대상 row의 lock을 기다리다가 lock을 쥔
트랜잭션이 커밋되면(EvalPlanQual), **그 row 자신**은 최신 커밋 버전으로
재평가되지만 **그 UPDATE 문의 subquery가 참조하는 다른 테이블**은
원래 그 UPDATE 문이 시작될 때 잡힌 snapshot으로 평가된다.
`ImportBatchRepository.completeIfNoPending()`의 `NOT EXISTS (SELECT ...
FROM import_candidates ...)`가 정확히 이 패턴이다.

ADR-0022 결정 4는 "candidate 생성 경로(`findByIdForUpdate`,
`PESSIMISTIC_WRITE`)와 complete()의 conditional UPDATE가 같은
`import_batches` row lock을 두고 경쟁하므로 나중 커밋은 항상 최신
상태를 보고 올바르게 성공/409를 결정한다"고 가정했는데, 실제로는
**complete()가 애초에 그 row lock을 아예 획득하지 않는다** —
`completeIfNoPending`은 단일 conditional UPDATE일 뿐 `findByIdForUpdate()`를
호출하지 않는다. 자세한 원인/대안 분석은 `docs/DECISIONS.md`의
**ADR-0025**(ADR-0022 결정 4 정정)를 먼저 읽는다.

approve/reject concurrency(`transitionIfPending`, ADR-0022 결정 2)는
이 문제가 없다 — 그 UPDATE의 조건(`status='PENDING'`)이 잠그는 row
자신의 컬럼만 재확인하고 다른 테이블을 참조하지 않기 때문이다.

**Claude가 이 수정을 로컬에서 실제로 적용해 검증 완료**(ADR-0025의
결정 그대로): 수정 후 `ImportCandidateConcurrencyTest` 25회 반복 전부
통과(0/25 실패, 수정 전 기준선 22/35 실패와 대비), 전체 스위트

## Scope

`ImportBatch.complete()`가 candidate 생성 경로와 동일한
`findByIdForUpdate()`(`@Lock(PESSIMISTIC_WRITE)`) 잠금을 사용하도록
바꾸고, "PENDING candidate 없음" 확인을 그 잠금 **이후의 별도 SELECT
문**으로 분리한다. 테스트 코드는 변경하지 않는다(기존
`ImportCandidateConcurrencyTest`가 이미 이 버그를 정확히 잡아냈고,
CountDownLatch 기반 동시 시작/추적된 ID 기반 cleanup/scoped assertion
모두 적절하므로 그대로 둔다).

## Technical Notes

- ADR-0025(`docs/DECISIONS.md`)를 구현 전에 읽는다 — 이번 diff의 근거가
  거기 있다.
- `findByIdForUpdate()`는 `import_candidates` 생성 경로
  (`ImportCandidateService.create()`)가 이미 쓰고 있는 메서드를 그대로
  재사용하는 것이다 — 신규 lock 종류 도입이 아니다.
- `ImportBatch.markCompleted()`는 기존 `markExtracted()`와 같은 스타일의
  도메인 메서드다(naked setter 대신).
- 신규 production dependency 없음, migration 없음(스키마 변경 없음).
