## Context

COLLECT-004부터 ALIO 상세조회(`/detail.do`)로 얻은 채용전형단계(`RecruitmentStep`)/
첨부파일(`Attachment`)이 DB에 저장되고 있지만, `GET /api/jobs/{id}` 응답에는
아직 노출되지 않는다(ADR-0013에서 저장까지만 다루고 조회 API는 의도적으로
남겨둔 부분, `docs/ROADMAP.md` "Phase 6 이후 후보" 항목).

이번 Phase 목표: DB에 이미 쌓이고 있는 `RecruitmentStep`/`Attachment`를
`GET /api/jobs/{id}` 상세조회 응답을 통해 실제로 사용할 수 있게 한다.
`GET /api/jobs` 목록/검색 응답에는 추가하지 않는다(payload 비대화 방지).
수집 인프라(ALIO 연동, Scheduler, enrichment 로직)는 이번 Phase에서 변경하지
않는다.

## Scope

1. **`GET /api/jobs/{id}` 응답 확장**: 기존 `JobPostingResponse`의 모든 필드를
   유지한 채 `recruitmentSteps: RecruitmentStepResponse[]`,
   `attachments: AttachmentResponse[]` 두 필드를 추가한 신규
   `JobPostingDetailResponse`(record)를 반환한다. steps/attachments가 없는
   경우(MANUAL 공고, 미보강 공고)는 `null`이 아니라 빈 배열을 반환한다.
2. **`RecruitmentStepResponse`(record)**: `sortNo`, `stepGroupName`,
   `competitionRate`, `applicantCount`, `recruitCount`, `occurredAtRaw` 6개
   필드만 포함한다. ALIO 내부 식별값(`recrutStepSn`/`minStepSn`/`maxStepSn`),
   엔티티 PK(`id`), 부모 참조(`jobPosting`), CareerOps 저장 시각(`createdAt`)은
   포함하지 않는다(사용자 승인 완료 — 지금 이 값들을 참조하는 별도 API가 없어
   노출 근거가 없다).
3. **`AttachmentResponse`(record)**: `sortNo`, `fileName`, `fileType`, `url`
   4개 필드만 포함한다. `recrutAtchFileNo`, `id`, `jobPosting`, `createdAt`은
   포함하지 않는다(위와 동일한 이유).
4. **정렬**: DB 조회 순서에 의존하지 않고 명시적으로 정렬한다.
   - `RecruitmentStep`: `sortNo ASC`, 동일 `sortNo` 내 `recrutStepSn ASC`
     (COLLECT-004에서 "관측 범위 내 전역 고유"로 확인된 값 — 안정적인
     secondary key. 응답에는 노출하지 않고 정렬에만 사용).
   - `Attachment`: `sortNo ASC`, 동일 `sortNo` 내 `recrutAtchFileNo ASC`
     (동일한 이유).
   - `RecruitmentStepRepository`/`AttachmentRepository`에 Spring Data 파생
     쿼리 메서드로 추가한다(`findByJobPostingIdOrderBySortNoAscRecrutStepSnAsc`,
     `findByJobPostingIdOrderBySortNoAscRecrutAtchFileNoAsc`). 기존
     `findByJobPostingId`(정렬 없음, COLLECT-004 테스트가 이미 사용 중)는
     그대로 두고 삭제/변경하지 않는다 — 새 메서드를 추가만 한다.
5. **Service 책임**: `JobPostingService.findById(Long id)`를 확장해
   `JobPostingDetailResponse`를 반환하도록 한다(Controller가 여러 Repository를
   직접 호출하지 않음). 흐름: `jobPostingRepository.findById()`(없으면 기존과
   동일하게 404 + `careerops.job.read{result=not_found}`) →
   `recruitmentStepRepository.findByJobPostingIdOrder...()` →
   `attachmentRepository.findByJobPostingIdOrder...()` → 조합해 반환.
   총 3개 query, `GET /api/jobs` 목록 경로(`search()`)는 무변경이므로 N+1 없음.
   `JobPostingService` 생성자에 `RecruitmentStepRepository`,
   `AttachmentRepository` 의존성을 추가한다. 새로운 Query Service 클래스는
   만들지 않는다(현재 규모에 비례하지 않는 과도한 계층).
6. **`JobPostingController.findById` 반환 타입**을 `JobPostingResponse` →
   `JobPostingDetailResponse`로 변경한다. 라우팅/경로/404 계약은 그대로.

## Out of Scope

- `GET /api/jobs` 목록/검색 응답에 steps/attachments 추가 — 하지 않는다
  (payload 크기 유지, 목적에 명시).
- 새 ALIO 수집 기능, 전체 history backfill, detail enrichment 재동기화,
  enrichment 동시성 재설계(ROADMAP "Phase 7 이후 후보"에 남아있는 별도 항목).
- 새 migration/DB 컬럼 — 기존 V3 스키마(`recruitment_steps`, `attachments`)로
  충분, 스키마 변경 없음.
- steps/attachments 개별 조회/수정/삭제 API, 페이지네이션(한 공고당 step/file
  개수가 많지 않아 불필요).
- `atchFileType` 코드 의미 매핑, `fileType`/`stepGroupName` 등 필드값 가공 —
  원본 그대로 전달.
- 파일 proxy/다운로드/재호스팅/malware 검사 — `url`은 ALIO 원본 URL을 그대로
  전달할 뿐.
- 새 Prometheus metric — 기존 `careerops.job.read` 카운터와 Actuator
  HTTP metric으로 충분하다고 판단, 추가하지 않는다.
- `EntityGraph`/fetch join 등 조회 성능 최적화 — 3-query 구조로 충분한
  단건 조회 규모.

### `JobPostingDetailResponse` 형태(참고)

```java
public record JobPostingDetailResponse(
        Long id, String companyName, String title, String employmentType,
        String careerLevel, String educationRequirement, String status,

    }

```

`JobPostingResponse`를 상속/재사용하지 않고 필드를 그대로 나열한다 — 이
프로젝트는 Lombok/MapStruct를 쓰지 않고(JOB-001 결정 유지) record는 상속이
불가능하므로, 기존 `JobPostingResponse`와 동일한 스타일로 별도 record를
만드는 것이 가장 단순하다.

### Service 예시 흐름

```java
public JobPostingDetailResponse findById(Long id) {
    JobPosting jobPosting = repository.findById(id)
            .map(jp -> { foundCounter.increment(); return jp; })
            .orElseThrow(() -> { notFoundCounter.increment(); return new ResponseStatusException(HttpStatus.NOT_FOUND); });
    List<RecruitmentStep> steps = recruitmentStepRepository
            .findByJobPostingIdOrderBySortNoAscRecrutStepSnAsc(id);
    List<Attachment> attachments = attachmentRepository
            .findByJobPostingIdOrderBySortNoAscRecrutAtchFileNoAsc(id);
    return JobPostingDetailResponse.from(jobPosting, steps, attachments);
}
```

기존 `findById`가 `JobPostingController`의 유일한 호출부임을 확인했으므로
(grep 결과), 메서드를 새로 추가하지 않고 기존 `findById`를 그대로 확장한다.
