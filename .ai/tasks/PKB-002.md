## Context

PKB-001(`CareerExperience`, `.ai/tasks/PKB-001.md`)로 서사형 경험 저장이
완료됐다. 이번 Phase(PKB-002/003/004)는 PKB를 확장해 경험 이외의 정형
프로필 정보(자격증/학력/수상)를 구조적으로 저장한다 — 목표는 "향후
이력서/포트폴리오 import와 JobPosting 매칭이 사용할 수 있는 안정적인
structured PKB schema를 완성한다"이다(ADR-0020).

`Certification`은 `CareerExperience`의 `type`으로 합치지 않고 독립
entity로 만든다(ADR-0018/ADR-0020). Certification/Education/Award는
상속 구조나 generic CRUD 없이 각각 독립 Task로 분리해 구현한다
(ADR-0020) — 이 Task는 그중 Certification만 다룬다. Education은
PKB-003, Award는 PKB-004.

## Scope

`Certification` entity 신설, 기존 `career` 패키지(신규 top-level 패키지
아님)에 CRUD API 추가.

기존 `CareerExperience`/`ExperienceBullet`/`ExperienceTag` 관련 파일과

### 2. Entity — `Certification`

```java
@Entity
@Table(name = "career_certifications")
public class Certification {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;

    @Column(nullable = false, length = 200)
    private String name;

    @Column(length = 200)
    private String issuer;

    private LocalDate acquiredDate;    // nullable

    private LocalDate expirationDate;  // nullable

    @Column(name = "credential_id", length = 100)
    private String credentialId;

    @Column(length = 2000)
    private String description;

    @CreationTimestamp private Instant createdAt;
    @UpdateTimestamp private Instant updatedAt;
    ...
}
```

Lombok 없음, getter + 명시적 `updateX()` mutator, protected no-arg 생성자
(`CareerExperience` 패턴 그대로 재사용). `@OneToMany`/양방향 관계 없음
(자식 entity가 없으므로 해당 사항 없음). `name`만 `nullable = false`이고
나머지 필드(날짜 포함)는 전부 nullable — 문서 import/과거 기록 입력 시
정확한 날짜를 모르는 경우를 막지 않기 위함(ADR-0020, PKB-001의
`startDate` nullable 결정과 동일 근거). `score` 필드는 만들지 않는다 —
시험마다 점수 체계가 근본적으로 다르므로(TOEIC 990점 만점/OPIc
등급/한능검 등급 등) 이번 entity에 억지로 섞지 않는다(사용자 결정,
Out of Scope 참고).

### 3. Migration — `V8__create_career_certifications_table.sql`

```sql
CREATE TABLE career_certifications (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    issuer VARCHAR(200),
    acquired_date DATE,
    expiration_date DATE,
    credential_id VARCHAR(100),
    description VARCHAR(2000),
    created_at TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    updated_at TIMESTAMP(6) WITH TIME ZONE NOT NULL
);
```

`career_` prefix + 복수형(기존 `career_experiences` 컨벤션). UNIQUE
제약/추가 index는 만들지 않는다 — 같은 이름의 자격증 재취득처럼 정당한
중복이 있을 수 있어 PK만으로 충분하다고 판단(ADR-0020). source/provenance/
vector/JSON/embedding/full-text index 없음.

### 4. Repository

```java
public interface CertificationRepository extends JpaRepository<Certification, Long> {
    @Query("SELECT c FROM Certification c ORDER BY c.acquiredDate DESC NULLS LAST")
    Page<Certification> findAllOrderByAcquiredDateDescNullsLast(Pageable pageable);
}
```

`JobPostingRepository`(`ORDER BY j.applicationEndAt ASC NULLS LAST`)의
JPQL `NULLS LAST` 문법을 그대로 재사용. 이번 Phase에는 filter가 없으므로
`CareerExperienceRepository.search()`처럼 조건부 `WHERE` 절이나 DTO
constructor projection을 쓸 필요가 없다 — entity를 그대로 반환하고
Service에서 DTO로 매핑한다.

### 5. Service — `CertificationService`

단일 row CRUD이며 부모+자식 aggregate가 아니므로 **`@Transactional`을
붙이지 않는다**(ADR-0015 무-트랜잭션 컨벤션 유지, ADR-0019/PKB-001의
`@Transactional`은 부모+자식 다중 row 원자적 쓰기라는 예외 조건에서만
적용된 것이지 기본값이 아니다 — ADR-0020).

```java
@Service
public class CertificationService {
    // create/findAll/findById/update/delete
    // find(id): repository.findById(id).orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND))
    // validateDates(acquiredDate, expirationDate): expirationDate가 acquiredDate보다
    //   빠르면 400 (CareerExperienceService.validateDates() 패턴 재사용, 둘 다 있을 때만 검증)
}
```

- `create()`: `validateDates()` 호출 후 저장.
- `update()`(PATCH): 요청 필드가 `null`이면 무변경(기존 컨벤션). 날짜
  cross-field 검증은 병합된 값(요청값 없으면 기존값 유지) 기준으로 수행
  (`CareerExperienceService.update()`의 `start`/`end` 병합 패턴 재사용).
- `delete()`: 존재하지 않으면 404, 있으면 hard delete.

### 6. Controller

```
POST   /api/career/certifications        -> 201, CertificationResponse
GET    /api/career/certifications        -> 200, CertificationListResponse (pagination only)
GET    /api/career/certifications/{id}   -> 200, CertificationResponse / 404
PATCH  /api/career/certifications/{id}   -> 200, CertificationResponse / 404
DELETE /api/career/certifications/{id}   -> 204 / 404
```

`CareerExperienceController` 구조 그대로 재사용(얇은 Controller, 검증/
조립은 Service). `GET` 목록은 `@PageableDefault(size = 20)` +
size 100 clamp(`Math.min(pageable.getPageSize(), 100)`, 기존 패턴).
클라이언트 지정 정렬/filter 파라미터 없음 — 정렬은 `acquiredDate DESC
NULLS LAST` 서버 고정(이번 Phase는 keyword/type 같은 filter를 추가하지
않는다 — 실제 소비자가 없는 상태에서 미리 만들지 않는다, Out of Scope).

### 7. DTO

**`CertificationCreateRequest`**:
```java
public record CertificationCreateRequest(
        @NotBlank @Size(max = 200) String name,
        @Size(max = 200) String issuer,
        LocalDate acquiredDate,
        LocalDate expirationDate,
        @Size(max = 100) String credentialId,
```

**`CertificationUpdateRequest`**: 위와 동일한 필드 전부 optional

**`CertificationResponse`**: `id`/`name`/`issuer`/`acquiredDate`/
`expirationDate`/`credentialId`/`description`/`createdAt`/`updatedAt`
(자식이 없으므로 summary/detail DTO 분리 없이 단일 flat DTO로 목록/
단건 조회 모두에 사용 — `JobApplicationResponse` 패턴).

**`CertificationListResponse`**: `content: List<CertificationResponse>`,
`totalElements`/`totalPages`/`page`/`size`(`CareerExperienceListResponse`
패턴 그대로).

## Out of Scope

- `score` 필드(어학/시험 점수) — 시험마다 점수 체계가 근본적으로 달라
  단일 필드로 통합하지 않는다. 필요하면 후속 `ProfileFact`(가칭) 후보로
  분리한다.
- `sourceType`/`sourceReference`(provenance) — 이번 Phase의 유일한 생성
  경로가 수동 입력뿐이라 지금 추가하면 죽은 컬럼이 된다. 문서 import
  Task 설계 시 additive migration으로 추가한다.
- keyword/issuer 검색 filter — 실제 소비자(UI)가 없는 상태에서 미리
  만들지 않는다.
- `ExperienceTag` 같은 공용 tag 시스템 복제 — `name`/`issuer` 필드로도
  구조화된 검색이 가능해 이번 Phase 매칭에 추가 가치가 없다.
- `JobPosting`과의 FK, 매칭 로직, 적합도 점수, 자기소개서 생성.
- AI/RAG/embedding/pgvector/semantic search.
- PDF/DOCX import, OCR, LLM extraction.
- 사용자 인증/다중 사용자, Frontend, Calendar/알림.

## Technical Notes

- 기존 `job`/`collector`/`application` 패키지, `CareerExperience` 관련
  파일은 이번 Task에서 수정하지 않는다.
- Entity/Repository/Service/Controller/DTO는 `CareerExperience`
  (`.ai/tasks/PKB-001.md`) 패턴을 그대로 재사용하되, **`@Transactional`은
  붙이지 않는다**(부모+자식 aggregate가 아님, ADR-0020) — 이 차이를
  명확히 인지하고 구현할 것.
- `NULLS LAST` JPQL 문법은 `JobPostingRepository`(`backend/src/main/java/
  com/careerops/backend/job/JobPostingRepository.java`)에 실사용 전례가
  있다.
- validation cross-field 검증은 `CareerExperienceService.validateDates()`
  패턴(Service 내 수동 검증 + `ResponseStatusException(BAD_REQUEST, msg)`)을
  재사용한다 — `@ControllerAdvice`/`@AssertTrue` 같은 새 메커니즘을
  도입하지 않는다(IMPORT-001/docs/METRICS.md 원칙).
- 신규 production/test dependency 없음.
