## Context

PKB-005는 `SourceDocument`(원문 등록)/`ImportBatch`(검토 작업 단위) provenance
등록 기반만 만들었다. `ImportCandidate`(검토 후보)와 승인/거부 흐름, 승인 시
실제 PKB(`CareerExperience`/`Certification`/`Education`/`Award`)에 반영하는
로직은 의도적으로 이번 Task(PKB-006)로 미뤄뒀다(ADR-0021).

이번 Task의 목표: "`SourceDocument`/`ImportBatch`에서 추출된 구조화 정보
후보를 `ImportCandidate`로 저장하고, 사용자가 검토하여 APPROVE한 후보만 실제
PKB에 반영하며, 어떤 candidate에서 생성된 PKB 데이터인지 provenance를 추적할
수 있도록 한다." LLM extraction은 이번 Task에서 구현하지 않는다 —
`ImportCandidate`는 API로 수동 생성해 검토/승인 흐름만 먼저 완성한다(PKB-008
후보에서 같은 candidate 생성 service를 LLM extractor가 재사용할 것을 전제로
설계한다).

설계 근거는 ADR-0021(3계층 provenance 모델 전체 방향)과 ADR-0022(이번 Task가
구체화한 candidate 상태 머신/concurrency/재사용/`ImportBatch` lifecycle)에
기록되어 있다 — 구현 시 두 ADR을 먼저 읽는다.

## Scope

기존 `com.careerops.backend.pkbimport` 패키지에 `ImportCandidate` entity +
승인/거부 흐름을 추가하고, `com.careerops.backend.career`(`CareerExperience`/
`Certification`/`Education`/`Award`) 4개 entity에 provenance 컬럼을 추가한다.
`ImportBatch`에 명시적 `complete` API를 추가한다.

### 3. `CandidateTargetType` / `ImportCandidateStatus` enum (신규, `EnumType.STRING`)

### 6. Candidate payload validation (ADR-0021 결정 2 구체화)

- **생성 시**: `targetType`에 대응하는 `*CreateRequest`(`CareerExperienceCreateRequest`
  / `CertificationCreateRequest` / `EducationCreateRequest` /
  `AwardCreateRequest`)로 `payload` 문자열을 Jackson(`tools.jackson.databind.ObjectMapper`,
  이 프로젝트는 Jackson 3)으로 역직렬화한 뒤, 주입받은
  `jakarta.validation.Validator`로 프로그래밍 방식 `validate()`를 호출한다.
  violation이 있으면 400 — 메시지에는 필드 경로 + 제약조건 메시지만 담고
  payload 원문 값은 포함하지 않는다. Jackson 역직렬화 자체가 실패하면(JSON
  문법 오류/타입 불일치) 파서 예외의 원문 메시지를 그대로 노출하지 않고
  `"invalid payload for targetType " + targetType` 같은 고정 메시지로 감싸
  400을 반환한다(파서 예외 메시지에 payload 원문 조각이 포함될 수 있어
  privacy 원칙과 충돌하기 때문).
- **승인 시**: 같은 방식으로 재역직렬화 + 재검증한 뒤 §5의 대상 Service
  `create(request, IMPORT, candidateId)`를 호출한다 — 이 호출이 각 Service에
  이미 있는 business-rule 검증(날짜 순서, GPA 범위 등)까지 그대로 적용한다.
  검증 로직을 candidate 쪽에 별도로 복제하지 않는다.

### 7. Approve/Reject — transaction + concurrency (ADR-0022 결정 2)

`ImportCandidateService.approve(batchId, candidateId)`/`reject(batchId,
candidateId)` 모두 `@Transactional`.

**Repository**:
```java
@Modifying
@Query("UPDATE ImportCandidate c SET c.status = :newStatus, c.reviewedAt = :reviewedAt " +
       "WHERE c.id = :id AND c.importBatch.id = :batchId AND c.status = 'PENDING'")
int transitionIfPending(@Param("id") Long id, @Param("batchId") Long batchId,
                         @Param("newStatus") ImportCandidateStatus newStatus,
                         @Param("reviewedAt") Instant reviewedAt);
```

**Approve 순서**:
1. `transitionIfPending(id, batchId, APPROVED, now())` 실행 — 이 UPDATE가
   트랜잭션의 첫 statement.
2. 영향 row 0건 → 원인 진단: candidate가 없거나 `batchId` 불일치면 404,
   존재하지만 이미 `APPROVED`/`REJECTED`면 409.
3. 영향 row 1건 → 같은 트랜잭션에서 candidate 재조회, §6 방식으로 payload
   재검증, 대상 Service `create(request, IMPORT, candidateId)` 호출, 결과
   entity의 id를 `candidate.createdEntityId`에 설정.
4. 3에서 예외(검증 실패 등)가 나면 `@Transactional`이 1의 UPDATE까지 포함해
   전부 롤백 — candidate는 `PENDING`으로 남고 PKB row도 생성되지 않는다.

**Reject 순서**: `transitionIfPending(id, batchId, REJECTED, now())`만
실행하고 종료(PKB row 생성 없음). 0건이면 approve와 동일한 방식으로
404/409 구분.

이 순서 자체가 동시 approve 요청에 대한 안전장치다 — conditional UPDATE가
대상 row에 암묵적 row-level lock을 걸기 때문에 동시에 두 approve 요청이
들어와도 반드시 하나가 다른 하나의 커밋을 기다린 뒤 최신 상태로 WHERE를
재평가하게 되어 PKB row가 두 개 생성될 수 없다. 별도 `@Lock` 애노테이션은
쓰지 않는다.

### 8. `ImportBatch` — 명시적 complete API + invariant 강제 (ADR-0022 결정 4)

**스키마 변경 없음** — `import_batches.status`/`completed_at`은 PKB-005(V12)
에서 이미 존재한다.

**`ImportBatchService.complete(Long batchId)`**(`@Transactional`):
```java
@Modifying
@Query("UPDATE ImportBatch b SET b.status = 'COMPLETED', b.completedAt = :now " +
       "WHERE b.id = :id AND b.status = 'OPEN' " +
       "AND NOT EXISTS (SELECT 1 FROM ImportCandidate c " +
       "                WHERE c.importBatch.id = b.id AND c.status = 'PENDING')")
int completeIfNoPending(@Param("id") Long id, @Param("now") Instant now);
```
영향 row 0건이면 원인 진단(존재하지 않음→404, 이미 COMPLETED→409, PENDING
candidate 존재→409). reopen(`COMPLETED→OPEN`) API는 만들지 않는다.

**Candidate 생성 시 부모 batch 상태 확인 — pessimistic lock**(complete()의
conditional UPDATE와 유일하게 경쟁하는 쓰기 경로이므로):
```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT b FROM ImportBatch b WHERE b.id = :id")
Optional<ImportBatch> findByIdForUpdate(@Param("id") Long id);
```
`ImportCandidateService.create(batchId, request)`는 이 메서드로 batch를 잠근
뒤 `status == OPEN`을 확인하고(아니면 409), 통과하면 같은 트랜잭션 안에서
candidate를 `PENDING`으로 저장한다. `complete()`의 UPDATE와 candidate
생성의 `SELECT ... FOR UPDATE`가 같은 `import_batches` row lock을 두고
경쟁하므로, 어느 쪽이 먼저 커밋되든 나중 쪽은 항상 최신 상태를 보고 올바르게
성공/409를 결정한다 — "COMPLETED batch는 PENDING candidate를 가질 수 없다"는
불변식이 이 lock으로 구조적으로 보장되고, 그 덕분에 approve/reject는
batch 상태를 별도로 재확인할 필요가 없다(§7의 candidate-level 상태 체크만
으로 충분 — COMPLETED batch에는 애초에 PENDING candidate가 존재할 수 없기
때문).

### 10. Controller / API

**`ImportCandidateController`** (`@RequestMapping("/api/career/imports/batches/{batchId}/candidates")`):

`createdAt DESC` 서버 고정 정렬. approve/reject는 상태 전이 command라 action
endpoint를 쓴다(PATCH 하나로 통합하지 않음).

## Acceptance Criteria

- [ ] `[자동]` `POST .../candidates` — 4개 `targetType` 각각에 대해 유효한
      payload로 요청 시 201, `status="PENDING"`, `createdEntityId` null.
- [ ] `[자동]` `POST .../candidates` — payload가 대상 `*CreateRequest`
      validation을 위반(예: `CAREER_EXPERIENCE`인데 `title` 누락)하면 400,
      row 미생성.
- [ ] `[자동]` `POST .../candidates` — payload가 JSON으로 파싱 불가하면 400
      (원문 파서 예외 메시지가 응답에 노출되지 않음을 확인).
- [ ] `[자동]` `POST .../candidates` — 존재하지 않는 `batchId`면 404.
- [ ] `[자동]` `POST .../candidates` — `COMPLETED` batch에 요청하면 409, row
      미생성.
- [ ] `[자동]` `GET .../candidates` — pagination + `status` 필터 동작.
- [ ] `[자동]` `GET .../candidates/{id}` — 존재 시 200, 다른 batch의
      candidate를 잘못된 `batchId` 경로로 조회하면 404.
- [ ] `[자동]` approve — `CAREER_EXPERIENCE` candidate 승인 시 200,
      `status="APPROVED"`, 실제 `CareerExperience` row가 생성되고

## Technical Notes

- ADR-0021, ADR-0022를 구현 전에 먼저 읽는다 — 이번 명세의 모든 설계
  결정의 근거가 그 두 ADR에 있다.
- `payload`/candidate 원문을 로그(`log.info`/`log.debug`)에 출력하지 않는다
  (PKB-005의 `rawText` 로그 금지 원칙과 동일 등급 — candidate payload도
  이력서/포트폴리오 내용을 담을 수 있다).
- Jackson은 이 프로젝트 전체가 Jackson 3(`tools.jackson.databind`)를
  사용한다 — `com.fasterxml.jackson.databind`(Jackson 2) import 실수를
  반복하지 않는다(PKB-005 round 2에서 실제로 발생한 문제,
  `docs/ARCHITECTURE.md` "Jackson 3가 기본" 참고). `jackson-annotations`만
  예외적으로 `com.fasterxml.jackson.annotation` 패키지를 유지한다.
- `Repository.search()`/신규 `@Query` 전부 파라미터가 매핑된 컬럼과 직접
  비교되는 형태만 쓴다(FIX-001 재발 방지).
- `@Modifying @Query` 메서드는 기본적으로 영속성 컨텍스트를 우회하므로,
  같은 트랜잭션에서 그 직후 entity를 다시 읽어야 하는 경우
  (`clearAutomatically`/재조회) Hibernate stale entity 문제가 나지 않게
  주의한다 — PKB-001/APPLICATION-002에서 반복 발생한 "Hibernate persistence
  context" 클래스의 문제를 참고(`CareerExperienceControllerTest`,
  `ApplicationStageControllerTest`의 기존 해결 패턴 참고).
- 신규 production dependency 없음. `jakarta.validation.Validator`는 이미
  `spring-boot-starter-validation` 계열로 존재하는 bean을 주입받아 쓴다.
