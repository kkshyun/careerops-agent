## Context

CareerOps는 채용공고 수집(JobPosting/ALIO)과 지원관리(JobApplication/
ApplicationStage)까지 완료했다. 이번 Phase부터 CareerOps의 핵심 차별화
영역인 Personal Knowledge Base(PKB, `docs/PROJECT.md`/`docs/ARCHITECTURE.md`
`docs/ROADMAP.md` "Phase 3 이후 후보" 참고)를 시작한다.

PKB는 향후 (1) JobPosting과 사용자 경험 매칭, (2) 특정 공고에 활용할 경험
추천, (3) 자소서 문항에 맞는 경험 검색, (4) 면접 준비 시 관련 경험 검색,
(5) 향후 embedding/RAG의 원천 데이터로 쓰일 예정이다. 이번 Task는 그
직전 단계로, **사람이 입력한 경험 데이터를 안정적으로 저장/조회하는 PKB
Core만** 만든다. AI/RAG/embedding/문서 import는 다루지 않는다
(ADR-0018/0019, 아래 Out of Scope 참고).

데이터 모델은 범용 `CareerItem`(자격증/학력/수상까지 통합) 대신 경험 중심
`CareerExperience`로 확정했다(ADR-0018) — 사용자 승인 완료.

## Scope

`CareerExperience` + 자식 `ExperienceBullet`/`ExperienceTag` entity 신설,
`career`(신규 top-level 패키지) 하위에 CRUD API.

```sql

    bullet_type VARCHAR(50),

    sort_order INTEGER NOT NULL,
    created_at TIMESTAMP(6) WITH TIME ZONE NOT NULL,

CREATE TABLE experience_tags (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    career_experience_id BIGINT NOT NULL REFERENCES career_experiences(id) ON DELETE CASCADE,
    keyword VARCHAR(50) NOT NULL,
    created_at TIMESTAMP(6) WITH TIME ZONE NOT NULL
);

CREATE UNIQUE INDEX uk_experience_tags_experience_keyword
    ON experience_tags (career_experience_id, LOWER(keyword));
```

`career_experiences`/`experience_bullets`/`experience_tags` 3테이블을
V3(RecruitmentStep+Attachment) 선례처럼 **하나의 migration 파일**로
함께 만든다. 두 자식 FK 모두 `ON DELETE CASCADE`(아래 12번 근거).
`uk_experience_tags_experience_keyword`는 **표현식 인덱스**(`LOWER(keyword)`)로
작성해야 한다 — plain UNIQUE 제약(`CONSTRAINT ... UNIQUE`)으로는
대소문자 무시를 표현할 수 없다. vector/pgvector/JSON dump/full-text
index/AI metadata/User FK는 만들지 않는다.

### 8. `CareerExperienceService`에 Service-level `@Transactional`

`create()`/`update()`/`delete()`는 `@Transactional`로 감싼다(ADR-0019 —
이 프로젝트 첫 사례, ADR-0015의 무-트랜잭션 전제가 부모+자식 다중 row
원자적 쓰기에는 적용되지 않는다는 예외). `findById()`/`findAll()`(read
전용)에는 붙이지 않는다.

### 9. bullets/tags 저장·수정 방식 — 전체 교체(delete-then-insert)

생성/수정 모두 `bullets`/`tags`는 **부모와 함께 원자적으로 저장**된다.
- 생성 시: 요청에 포함된 순서대로 `sortOrder`를 0부터(또는 1부터,
  구현 시 일관되게) 자동 할당해 `ExperienceBullet`을 insert한다.
  `ExperienceBulletRequest`에는 `sortOrder` 필드 자체가 없다 — 배열
  순서(index)가 곧 `sortOrder`다. 사용자가 명시적으로 `sortOrder`를
  지정하는 경로는 없으므로 "중복 sortOrder 409" 케이스가 존재하지 않는다.
- 수정 시(PATCH): 요청의 `bullets`/`tags` 필드가:
  - **필드 자체가 생략되거나 JSON `null`** → 기존 bullets/tags 전체
    무변경.
  - **빈 배열 `[]`** → 기존 bullets(또는 tags) 전체 삭제.
  - **값이 있는 배열 `[...]`** → 기존 bullets(또는 tags)를 전부 삭제하고
    요청 배열 내용으로 다시 insert(diff/merge 아님, 통째로 교체). 배열
    순서가 새 `sortOrder`가 된다.
  - bullets와 tags는 서로 독립적으로 판단한다(예: bullets는 교체, tags는
    무변경도 가능).
- tags 저장 시 대소문자 무시 dedup을 적용한다(6번). 빈 문자열/공백만
  있는 tag는 저장하지 않는다(무음으로 제외, 에러 아님).

이 전체 교체 PATCH는 이 프로젝트 최초의 List 필드 PATCH 컨벤션이다 —
Jackson이 JSON `null`과 `[]`를 서로 다른 Java 값(`null` vs 빈 `List`)으로
역직렬화하는 성질을 이용한다.

### 10. API

```
POST   /api/career/experiences        -> 201, CareerExperienceDetailResponse
GET    /api/career/experiences        -> 200, CareerExperienceListResponse (type/keyword filter, pagination)
GET    /api/career/experiences/{id}   -> 200, CareerExperienceDetailResponse / 404
PATCH  /api/career/experiences/{id}   -> 200, CareerExperienceDetailResponse / 404
DELETE /api/career/experiences/{id}   -> 204 / 404
```

- `GET` 목록: `type`(정확 일치, optional) + `keyword`(`title` `ILIKE`
  부분일치, optional) 필터. AND 조합(둘 다 지정 시 둘 다 만족). 정렬은
  `updatedAt DESC` 고정(클라이언트 지정 정렬 없음 — JOB-002/APPLICATION-001
  선례). `Pageable` + `@PageableDefault(size=20)`, size 100으로 clamp(기존
  패턴).
- `POST`/`PATCH` 응답이 `CareerExperienceDetailResponse`(bullets+tags
  포함)인 것은 기존 컨벤션(`JobApplicationResponse`는 flat)과 다른
  지점이다 — bullets/tags가 부모와 **같은 요청에서 원자적으로
  생성/교체**되므로, 클라이언트가 추가 GET 없이 저장된 자식 상태를
  바로 확인할 수 있게 한다.
- 목록(`GET /api/career/experiences`)은 `CareerExperienceResponse`(자식
  없는 flat DTO)만 반환 — bullets/tags Repository를 목록 쿼리 경로에서
  전혀 참조하지 않아 N+1을 만들지 않는다(APPLICATION-002 검증 방식과
  동일하게, "자식 Repository 미참조"로 N+1 부재를 증명).

### 11. Request/Response DTO 초안

**`CareerExperienceCreateRequest`**:
```json
{ "type": "PROJECT", "title": "사내 추천 시스템 고도화",
  "organization": "OO회사", "role": "백엔드 개발",
  "startDate": "2025-03-01", "endDate": "2025-08-31",
  "summary": "추천 응답시간 40% 단축",
  "detail": "기존 추천 파이프라인의 병목을 분석해...",
  "bullets": [
    { "bulletType": "CONTEXT", "content": "일 평균 트래픽 급증으로 추천 API p99 지연이 800ms까지 증가" },
    { "bulletType": "ACTION", "content": "캐시 계층 추가 및 쿼리 배치화로 재구성" },
    { "bulletType": "RESULT", "content": "p99 지연 800ms -> 480ms로 40% 단축" }
  ],
  "tags": ["Spring Boot", "Redis", "PostgreSQL", "성능 개선"] }
```
- `type`: `@NotNull`.
- `title`: `@NotBlank @Size(max=200)`.
- `organization`/`role`: `@Size(max=200)`, optional.
- `startDate`/`endDate`: optional. `endDate < startDate`면 400.
- `summary`: `@Size(max=500)`, optional. `detail`: `@Size(max=4000)`, optional.
- `bullets`: optional list(생략 시 빈 리스트로 저장). 각 원소
  `content`: `@NotBlank @Size(max=1000)`, `bulletType`: optional.
- `tags`: optional list(생략 시 빈 리스트). 각 원소
  `@NotBlank @Size(max=50)`. 같은 요청 안 대소문자 무시 중복은
  dedup(에러 아님).

**`CareerExperienceUpdateRequest`**: 위와 동일한 필드 전부 optional
(PATCH, null=무변경). `bullets`/`tags`는 9번 규칙(null=무변경,
`[]`=전체삭제, `[...]`=전체교체).

**`CareerExperienceResponse`**(목록용): id/type/title/organization/role/
startDate/endDate/summary/createdAt/updatedAt.

**`CareerExperienceDetailResponse`**: 위 필드 전부 + detail +
`bullets: List<ExperienceBulletResponse>`(sortOrder ASC) +
`tags: List<String>`.

**`ExperienceBulletResponse`**: `{ "bulletType": "ACTION", "content": "...", "sortOrder": 1 }`
(id는 응답에 포함하지 않는다 — 전체 교체 방식이라 클라이언트가 개별
bullet id를 참조할 필요가 없다).

### 12. 삭제/cascade 정책

`CareerExperience` 삭제 시 `experience_bullets`/`experience_tags`는
DB `ON DELETE CASCADE`로 함께 삭제된다(ApplicationStage/ADR-0017과 동일
논리 — bullets/tags는 부모 경험 없이는 독립적 의미가 없는 진짜 aggregate
내부 데이터). Entity에는 `@OneToMany`/양방향 관계를 추가하지 않는다.
Hard delete만 지원(소프트 삭제 없음 — 기존 컨벤션 전체와 일관).

### 13. custom metric

추가하지 않는다. 일반 CRUD이므로 기존 Spring HTTP metric으로 충분
(APPLICATION-001/002와 동일 판단).

## Out of Scope

- Certification/Education/Award 엔티티(ADR-0018 — 향후 별도 Task).
- `sourceType`/`sourceReference`(생성 출처 추적) — 이번 Phase의 유일한
  생성 경로가 수동 입력뿐이라 지금 추가하면 죽은 컬럼이 된다. 문서
  import(PKB-002 후보) 설계 시 additive migration으로 추가한다.
- AI/RAG/embedding/pgvector/semantic search/full-text search.
- JobPosting ↔ CareerExperience 매칭, 적합도 점수, 자기소개서 생성,
  면접 질문 생성.
- Skill 마스터 엔티티, 동의어/전역 taxonomy 정규화(6번 — 같은 경험 내
  대소문자 dedup만 한다).
- 별도 `Metric`(정량 성과) 엔티티 — 수치는 summary/detail/bullet
  content의 자유 텍스트로 표현한다.
- JSON Merge Patch 표준 도입 — 스칼라 필드는 기존 null=무변경 컨벤션
  유지(String을 "빈 값으로 지우기"는 여전히 불가, 기존 프로젝트 전체의
  알려진 한계). bullets/tags만 9번의 전용 배열-교체 컨벤션을 새로 쓴다.
- bullet/tag 단건 CRUD API(개별 bullet PATCH/DELETE 등) — 항상 부모
  `CareerExperience`를 통한 전체 교체만 지원.
- 사용자 인증/다중 사용자, User/UserProfile FK.
- Frontend, Calendar, 알림, 수집 인프라 개선.

## Technical Notes

- 기존 `job`/`collector`/`application` 패키지는 이번 Task에서 수정하지
  않는다. 신규 `career` 패키지만 추가한다.
- Entity/Repository/Service/Controller/DTO는 `ApplicationStage`
  (`.ai/tasks/APPLICATION-002.md`)의 패턴을 그대로 재사용한다: Lombok
  없음, `@ManyToOne(optional=false, fetch=LAZY)` 단방향 FK, record DTO,
  `EnumType.STRING`.
- bullets/tags 전체 교체(9번)는 이 프로젝트 최초의 List 필드 PATCH
  패턴이다 — 구현 시 `null`(무변경)과 `[]`(전체삭제)를 반드시 구분해야
  한다(Jackson 기본 역직렬화로 자연스럽게 구분됨, 별도 설정 불필요하나
  DTO 필드 타입이 `List<...>`이고 primitive default가 섞이지 않게 주의).
- `uk_experience_tags_experience_keyword`는 `CREATE UNIQUE INDEX ...
  ON ... (career_experience_id, LOWER(keyword))` 표현식 인덱스로 작성 —
  table-level `CONSTRAINT ... UNIQUE`로는 만들 수 없다(PostgreSQL 제약).
- `CareerExperienceService.create()`/`update()`/`delete()`에
  `@Transactional` 적용(ADR-0019). `findById()`/`findAll()`은 read
  전용이라 붙이지 않는다.
- 신규 production/test dependency 없음.
