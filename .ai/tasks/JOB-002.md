## Context

COLLECT-002까지 완료되어 ALIO 채용공고가 `JobPosting`에 `status`(진행/마감),
`careerLevel`(경력구분), `educationRequirement`(필요학력), `institutionCode`
(기관코드) 등을 포함해 DB에 쌓이고 있다. 그러나 현재 `JobPostingController`는
`POST /api/jobs`(생성)와 `GET /api/jobs/{id}`(단건 조회)만 제공하고, 여러 건을
조건에 맞게 탐색하는 API가 없다 — 사용자가 실제로 "지금 지원 가능한 신입
공고가 뭐가 있는지" 확인할 방법이 아직 없다.

`docs/ROADMAP.md` "Phase 2 이후 후보"에 이미 "조회/필터링 API 확장" 항목으로
候補로 남아 있었고, 이번에 사용자가 명시적으로 우선순위를 정해 착수를
승인했다. ALIO 수집 구조나 외부 API 연동(COLLECT-00x)은 이번 Task에서 변경하지
않는다 — 이미 DB에 저장된 `JobPosting`을 조회하는 것만 다룬다(요청마다 ALIO를
재호출하지 않음).

## Scope

`JobPosting` 목록 조회 + 필터링 + 정렬 + pagination을 제공하는
`GET /api/jobs` 엔드포인트 1개를 신설한다.

1. **필터 4개** (모두 선택적, 값이 없으면 조건 미적용):
   - `status` — 정확 일치 (예: `OPEN`, `CLOSED`)
   - `careerLevel` — 부분 일치(`LIKE %value%`). ALIO `recrutSeNm` 값이
     `"신입"`/`"경력"`/`"신입+경력"` 등으로 나타나므로, `careerLevel=신입`
     조회 시 `"신입+경력"`도 매치되어야 신입 지원 가능 공고를 놓치지 않는다.
   - `companyName` — 부분 일치(`LIKE %value%`). 기관명을 정확히 모르는
     사용자도 검색 가능해야 한다.
   - `jobCategory` — 부분 일치(`LIKE %value%`). `AlioJobMapper`가
     `ncsCdNmLst`(콤마로 이어진 NCS 직무 목록 문자열, 예:
     `"정보기술,경영·행정·사무"`)를 그대로 저장하므로 정확 일치로는 검색이
     거의 불가능하다.
   - 4개 필터는 AND 조합.
2. **정렬**: `applicationEndAt ASC NULLS LAST` 고정 1종만 제공(마감 임박순).
   클라이언트가 정렬 기준/방향을 선택하는 파라미터는 이번 Scope에 없다.
3. **Pagination**: `page`(0-based, 기본 0), `size`(기본 20, 최대 100 — 100
   초과 요청은 100으로 clamp) query parameter. Spring Data `Pageable` +
   `PageableDefault` 사용.
4. **응답 형식**: Spring Data `Page<T>`를 그대로 직렬화하지 않고, 신규
   `JobPostingListResponse` record로 감싼다 — `content`(`List<JobPostingResponse>`),
   `totalElements`(long), `totalPages`(int), `page`(int), `size`(int).
5. **구현 방식**: `JobPostingRepository`에 JPQL `@Query` 메서드 1개
   (`search(status, careerLevel, companyName, jobCategory, pageable)`)를
   추가한다. `(:param IS NULL OR ...)` 패턴으로 4개 필터를 한 쿼리에 처리하고,
   `ORDER BY j.applicationEndAt ASC NULLS LAST`를 쿼리에 고정 명시한다.
   `JobPostingService`/`JobPostingController`는 파라미터를 그대로 전달만
   하고 조건별 분기(if/else)를 만들지 않는다.

### JPQL 쿼리 참고 형태

```java
@Query("""
    SELECT j FROM JobPosting j
    WHERE (:status IS NULL OR j.status = :status)
      AND (:careerLevel IS NULL OR j.careerLevel LIKE CONCAT('%', :careerLevel, '%'))
      AND (:companyName IS NULL OR j.companyName LIKE CONCAT('%', :companyName, '%'))
      AND (:jobCategory IS NULL OR j.jobCategory LIKE CONCAT('%', :jobCategory, '%'))
    ORDER BY j.applicationEndAt ASC NULLS LAST
    """)
Page<JobPosting> search(
        @Param("status") String status,
        @Param("careerLevel") String careerLevel,
        @Param("companyName") String companyName,
        @Param("jobCategory") String jobCategory,
        Pageable pageable);
```

주의: 쿼리에 `ORDER BY`를 이미 고정 명시했으므로, Controller에서 만드는
`Pageable`은 `Sort`를 포함하지 않고(`PageRequest.of(page, size)`) page/size
정보만 사용한다. `Pageable`에 별도 `Sort`가 붙으면 JPQL의 고정 `ORDER BY`와
충돌/중복 정렬절이 생길 수 있으니 피한다.

### size 상한(clamp) 위치

Controller가 아니라 Service에서 처리한다(Repository 메서드 시그니처를
순수하게 유지) — 예: `int clampedSize = Math.min(size, 100)` 후
`PageRequest.of(page, clampedSize)` 생성.

### `JobPostingListResponse` 형태

```java
public record JobPostingListResponse(
        List<JobPostingResponse> content,
        long totalElements,
        int totalPages,
        int page,
        int size
) {
    public static JobPostingListResponse from(Page<JobPosting> page) {
        ...
    }
}
```

### LIKE 대소문자 민감도

Postgres 기본 `LIKE`는 대소문자를 구분한다. 이번 Task 대상 값(한글 기관명/
직무명, `status`는 대문자 고정값)은 실사용에서 영향이 적다고 판단해 `ILIKE`나
별도 정규화(LOWER) 도입은 하지 않는다 — 실사용 중 문제가 확인되면 재검토.

### Dependency

신규 production/test dependency 없음. Spring Data JPA의 `Pageable`/`Page`는
`spring-boot-starter-data-jpa`에 이미 포함.
