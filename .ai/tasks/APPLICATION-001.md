## Context

지금까지 CareerOps는 `JobPosting`(채용공고 자체)만 수집/저장/조회할 수 있었고,
사용자가 "이 공고에 지원하기로 했다/지원했다"를 기록할 방법이 없었다.
`docs/ROADMAP.md` Phase 8까지 JobPosting 수집·조회 파이프라인이 완료됐고,
이제 사용자가 관심 있는 채용공고를 자신의 지원 대상으로 등록하고 현재
지원 상태와 기본 정보(메모)를 관리하는 `JobApplication` 도메인을 새로
만든다.

단일 사용자 MVP이므로 User/Auth 도메인은 이번 Phase에서 추가하지 않는다.
전형 단계별 일정/결과(`ApplicationStage`), 자기소개서, 알림, Calendar 등은
모두 향후 Phase(APPLICATION-002 이후) 범위이며 이번 Task는 다루지 않는다.

## Scope

`JobApplication` entity 신설 + CRUD/상태 관리 REST API.

### 1. Entity — `com.careerops.backend.application.JobApplication`

```java
@Entity
@Table(name = "job_applications")
public class JobApplication {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;

    @ManyToOne(optional = false, fetch = FetchType.LAZY)
    @JoinColumn(name = "job_posting_id", nullable = false)
    private JobPosting jobPosting;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 50)
    private ApplicationStatus status;

    @Column(length = 2000)
    private String memo;

    private LocalDate appliedAt;

    @CreationTimestamp private Instant createdAt;
    @UpdateTimestamp private Instant updatedAt;
    ...
}
```

`RecruitmentStep`(`backend/src/main/java/com/careerops/backend/job/RecruitmentStep.java`)의
`@ManyToOne(optional = false, fetch = FetchType.LAZY) @JoinColumn` 패턴을 그대로
재사용한다 — `jobPostingId`를 raw `Long` 컬럼으로 두지 않는다.

### 2. `ApplicationStatus` enum (신규 Java enum, `EnumType.STRING`)

```java
public enum ApplicationStatus {
    INTERESTED,   // 관심 등록, 아직 지원 예정 확정 전
    PLANNED,      // 지원 예정 확정, 아직 제출 전
    SUBMITTED,    // 지원서 제출 완료, 전형 결과 대기(서류/필기/면접 세부 미추적)
    OFFERED,      // 합격/오퍼
    REJECTED,     // 불합격
    WITHDRAWN     // 지원 취소/철회
}
```

**의도적으로 넣지 않은 것**: `IN_PROGRESS`(의미가 모호하고 향후 `ApplicationStage`와
겹침), `DOCUMENT`/`WRITTEN`/`INTERVIEW`(전형 단계이지 지원 상태가 아님 — 향후
APPLICATION-002의 `ApplicationStage`가 담당). `status`는 "이 지원이 전체적으로
어느 국면인가"라는 요약값 역할만 하고, 전형 단계별 일정/결과는 다루지 않는다.

**기존 `JobPosting.status`(plain `String`, ALIO 원본 값 그대로 저장)와 다르게
진짜 Java enum을 쓰는 이유**: `JobPosting.status`는 외부(ALIO) 원본 문자열을
그대로 반영해야 해서 느슨한 `String`이 맞지만, `JobApplication.status`는
전적으로 내부 통제 어휘라 컴파일 타임 안정성과 잘못된 값 자동 400 처리
(Jackson deserialization 실패 → `HttpMessageNotReadableException` → 400)를
얻을 수 있는 enum이 더 적합하다.

### 3. Migration — `V5__create_job_applications_table.sql`

```sql
CREATE TABLE job_applications (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    job_posting_id BIGINT NOT NULL REFERENCES job_postings(id),
    status VARCHAR(50) NOT NULL,
    memo VARCHAR(2000),
    applied_at DATE,
    created_at TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    updated_at TIMESTAMP(6) WITH TIME ZONE NOT NULL,
    CONSTRAINT uk_job_applications_job_posting_id UNIQUE (job_posting_id)
);
```

`job_posting_id` FK에 `ON DELETE` 절을 넣지 않는다(`recruitment_steps`/
`attachments`의 V3 마이그레이션과 동일 컨벤션 — Postgres 기본 `NO ACTION`).
`CascadeType.ALL`도 Entity에 추가하지 않는다. `JobPosting` 삭제 API가 현재
존재하지 않으므로 지금 당장 동작에 영향은 없지만, 향후 삭제 API가 생겨도
사용자의 지원 이력이 조용히 함께 삭제되지 않도록 방어적으로 유지한다.

`status` 단독 index, `updated_at` 정렬용 index는 만들지 않는다(데이터량 적음,
과도한 인덱스 금지 원칙).

### 4. 중복 등록 정책 — 409 Conflict

같은 `jobPostingId`로 두 번째 `JobApplication`을 만들려는 요청은 **409
Conflict**로 거부한다(사용자 승인). 2중 방어:

1. 애플리케이션 사전 체크: `existsByJobPostingId(jobPostingId)`가 true면
   즉시 `ResponseStatusException(HttpStatus.CONFLICT)`.
2. DB `UNIQUE(job_posting_id)` 제약: 동시 요청 race로 사전 체크를 통과해도
   `save()`가 `DataIntegrityViolationException`을 던지면 이것도 409로
   변환한다(COLLECT-006의 `createOrGetExisting()`과 달리 **기존 row를
   반환하지 않고 실패로 처리** — 이번엔 사용자가 명시적으로 트리거하는
   액션이라 "이미 등록돼 있다"는 신호를 클라이언트가 명확히 받아야 한다).

### 5. API

```
POST   /api/applications          -> 201, JobApplicationResponse
GET    /api/applications          -> 200, JobApplicationListResponse (status 필터 + pagination)
GET    /api/applications/{id}     -> 200, JobApplicationResponse / 404
PATCH  /api/applications/{id}     -> 200, JobApplicationResponse / 404
DELETE /api/applications/{id}     -> 204 / 404
```

**`POST /api/applications`** — Request `JobApplicationCreateRequest`:
```json
{ "jobPostingId": 123, "status": "INTERESTED", "memo": "금융 IT 직무" }
```
- `jobPostingId`: `@NotNull`. 존재하지 않으면 404.
- `status`: optional — 생략(null) 시 서비스가 `ApplicationStatus.INTERESTED`로
  기본값 설정. 빈 문자열이 아니라 필드 자체 생략/`null`만 기본값 트리거로
  처리한다.
- `memo`: optional, `@Size(max = 2000)`.
- `appliedAt`: optional, `LocalDate`. **자동 설정 안 함** — status가
  SUBMITTED로 바뀌어도 서버가 임의로 오늘 날짜를 채우지 않는다(과거 지원
  건 소급 입력과 충돌 방지, 숨은 비즈니스 규칙 최소화 원칙). 사용자가 알고
  있으면 생성/수정 요청에 직접 넣는다.
- 같은 `jobPostingId` 중복 → 409(위 4번 참고).

**`PATCH /api/applications/{id}`** — Request `JobApplicationUpdateRequest`:
```json
{ "status": "SUBMITTED", "memo": "1차 서류 제출함", "appliedAt": "2026-08-18" }
```
필드가 요청 JSON에 없거나 `null`이면 "변경 없음"으로 처리한다(즉 PATCH로
`memo`를 지우고 싶으면 빈 문자열 `""`을 보낸다 — `null`은 무변경). 전체
치환(PUT)이 아니라 부분 수정만 지원한다.

**`GET /api/applications`** — query: `status`(optional, 정확 일치),
`page`/`size`(기존 `JobPostingController`와 동일한 `Pageable` +
`@PageableDefault(size = 20)` 컨벤션 재사용, size 최대 100 clamp는 Service
에서 처리). 정렬은 **`updatedAt DESC` 고정**(JOB-002처럼 클라이언트가 정렬
기준을 선택하는 파라미터는 없음).

**응답 DTO — `JobApplicationResponse`** (단건 조회/생성/수정/목록 항목에
전부 재사용, 별도 "Summary" DTO를 만들지 않음):
```json
{
  "id": 1,
  "status": "INTERESTED",
  "memo": "금융 IT 직무",
  "appliedAt": null,
  "createdAt": "2026-08-18T00:00:00Z",
  "updatedAt": "2026-08-18T00:00:00Z",
  "jobPostingId": 123,
  "companyName": "한국전력공사",
  "title": "신입 IT 개발자",
  "applicationEndAt": "2026-08-31",
  "jobPostingStatus": "OPEN"
}
```
`JobPosting` 전체 상세(recruitmentSteps/attachments 등)는 절대 중첩하지
않는다 — company/title/applicationEndAt/status 4개 snapshot 필드만 포함한다.

**목록 응답 — `JobApplicationListResponse`**: `JobPostingListResponse`와
동일한 형태(`content`, `totalElements`, `totalPages`, `page`, `size`).

### 6. Repository — N+1 방지 (JOB-003 원칙 재사용)

`JobApplicationRepository`에 JobPosting과 JOIN하는 JPQL constructor
expression을 만들어 목록/단건 조회 모두 **단일 쿼리**로 `JobApplicationResponse`를
직접 조립한다(엔티티를 따로 조회한 뒤 서비스에서 매핑하지 않음):

```java
@Query("""
    SELECT new com.careerops.backend.application.dto.JobApplicationResponse(
        a.id, a.status, a.memo, a.appliedAt, a.createdAt, a.updatedAt,
        p.id, p.companyName, p.title, p.applicationEndAt, p.status)
    FROM JobApplication a JOIN a.jobPosting p
    WHERE (:status IS NULL OR a.status = :status)
    ORDER BY a.updatedAt DESC
    """)
Page<JobApplicationResponse> search(@Param("status") ApplicationStatus status, Pageable pageable);

@Query("""
    SELECT new com.careerops.backend.application.dto.JobApplicationResponse(
        a.id, a.status, a.memo, a.appliedAt, a.createdAt, a.updatedAt,
        p.id, p.companyName, p.title, p.applicationEndAt, p.status)
    FROM JobApplication a JOIN a.jobPosting p
    WHERE a.id = :id
    """)
Optional<JobApplicationResponse> findResponseById(@Param("id") Long id);

boolean existsByJobPostingId(Long jobPostingId);
```

생성/수정 후에도 이 `findResponseById()`를 재사용해 응답을 조립한다(entity
저장과 응답 조립을 분리, `JobPostingDetailResponse.from(entity, ...)`처럼
entity 인자로 수동 매핑하지 않음 — 필드가 늘어나도 쿼리 하나만 손보면 됨).

### 7. Transaction boundary

`@Transactional`을 추가하지 않는다. `JobPostingService`(ADR-0015)와 동일하게
이 프로젝트는 `repository.save()`가 독립된 짧은 트랜잭션으로 끝나는 것을
전제로 하고, 생성 흐름(JobPosting 존재 확인 → 중복 확인 → save)은 여러 read
뒤에 단일 write 하나만 있어 명시적 트랜잭션 경계가 필요한 다중-write
업무가 아니다. race는 DB UNIQUE 제약이 최종적으로 막는다(4번 참고).

- 신규 production/test dependency 없음.
