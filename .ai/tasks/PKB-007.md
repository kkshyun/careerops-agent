## Context

PKB-005/006까지 `SourceDocument`는 사용자가 원문 텍스트를 API로 직접
붙여넣어야만 등록할 수 있었다(ADR-0021 결정 4가 파일 업로드/파싱을
명시적으로 배제). 이번 Task의 목표는 "사용자가 PDF 또는 DOCX 파일을
업로드하면 서버가 파일에서 텍스트를 추출하고, 그 결과를 기존
`SourceDocument`로 안전하게 등록할 수 있도록 한다"이다.

LLM extraction(추출된 rawText → `ImportCandidate` 자동 생성)은 이번
Task에서 구현하지 않는다 — PKB-008 후보로 남긴다. 이번 Task는
"파일 → text extraction → `SourceDocument`"까지만 완성한다.

설계 근거는 ADR-0023(parser dependency 선정, 원본 binary 미저장,
zip bomb 방어)에 기록되어 있다 — 구현 전 먼저 읽는다.

## Scope

기존 `com.careerops.backend.pkbimport` 패키지에 파일 업로드 API와 텍스트
추출 abstraction을 추가한다. `SourceDocument`/`ImportBatch`/
`ImportCandidate` 도메인 모델과 기존 rawText 직접 등록 API는 변경하지
않는다(신규 DB migration 없음 — `source_documents` 테이블은 이미 필요한
컬럼을 모두 갖고 있다).

### 1. 패키지 구조 (추가분)

```
backend/src/main/java/com/careerops/backend/pkbimport/
├── SourceDocumentController.java   (수정 — /upload 엔드포인트 추가)
├── SourceDocumentService.java      (수정 — createFromUpload() 추가)
└── extraction/
    ├── DocumentTextExtractor.java          (인터페이스)
    ├── DocumentExtractionException.java    (unchecked, 내부 전용)
    ├── PdfTextExtractor.java               (PDFBox 구현체)
    ├── DocxTextExtractor.java              (POI 구현체)
    └── DocumentTextExtractionService.java  (확장자 기반 dispatch)
```

기존 `career`/`job`/`collector`/`application`/`manualimport` 패키지는 전혀
수정하지 않는다. `ImportBatch`/`ImportCandidate` 관련 파일도 수정하지
않는다 — 이번 Task는 `SourceDocument` 생성 경로만 확장한다.

### 2. `build.gradle` — 신규 dependency 2개 (ADR-0023)

```groovy
implementation 'org.apache.pdfbox:pdfbox:3.0.8'
implementation 'org.apache.poi:poi-ooxml:5.5.1'
```
Spring Boot BOM이 두 라이브러리 버전을 관리하지 않으므로 버전을 직접
명시한다. 다른 신규 dependency는 추가하지 않는다(multipart 지원은
`spring-boot-starter-web`이 이미 전이의존성으로 갖는
`spring-boot-servlet`에 포함되어 있음 — 조사로 확인 완료).

### 3. `application.yml` — multipart 설정

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 10MB
      max-request-size: 11MB
```
`max-file-size`(10MB)는 파일 자체의 상한, `max-request-size`(11MB)는
multipart 인코딩 overhead(경계 문자열, 헤더, `documentType` part 등)를
감안한 요청 전체 상한이다. 이 값을 초과하면 Spring이
`MaxUploadSizeExceededException`을 던지는데, 이 예외는 Spring Framework
7의 `ErrorResponse` 인터페이스를 구현하고 있어 **별도
`@ExceptionHandler`/`@ControllerAdvice` 없이도 기본적으로 413 Payload Too
Large 응답을 만든다**(jar 내부 확인 완료) — 이 Task에서 새로운 전역 예외
처리 시스템을 만들 필요가 없다.

### 4. 텍스트 추출 abstraction

```java
public interface DocumentTextExtractor {
    boolean supports(String lowerCaseExtension);   // 예: "pdf", "docx"
    String extract(InputStream inputStream);        // 실패 시 DocumentExtractionException(unchecked)
}
```

`PdfTextExtractor`(PDFBox):
- `Loader.loadPDF(...)`로 로드 → `document.isEncrypted()`이면
  `DocumentExtractionException("password protected")`.
- `PDFTextStripper`로 전체 텍스트 추출(페이지 순서는 stripper 기본 동작이
  보존). 페이지 단위 metadata는 저장하지 않는다.
- `IOException`/`InvalidPasswordException` 등 파싱 실패는 라이브러리
  원문 메시지를 그대로 감싸지 않고 `DocumentExtractionException`으로
  변환(생성자에 원인은 cause로만 담고, 메시지는 프로젝트가 직접 정한
  고정 문자열 사용 — privacy 원칙, §8 참고).

`DocxTextExtractor`(POI):
- `new XWPFDocument(inputStream)`으로 로드.
- `document.getBodyElements()`를 순회하며 `XWPFParagraph`는 `getText()`,
  `XWPFTable`은 각 행의 셀 텍스트를 tab으로 join한 뒤 행 사이는
  개행으로 join — **문서에 등장하는 순서 그대로** 이어 붙인다(표를
  버리거나 끝에 몰아서 붙이지 않는다).
- POI의 `ZipSecureFile` 기반 zip bomb 방어는 기본값 그대로 사용한다
  (`setMinInflateRatio` 등을 완화하는 코드를 작성하지 않는다, ADR-0023).
- 파싱 실패(`POIXMLException`, `NotOfficeXmlFileException`, zip bomb
  감지 예외 등)는 PDF와 동일하게 고정 메시지로 감싸 변환한다.

`DocumentTextExtractionService`:
- `List<DocumentTextExtractor>`를 Spring이 주입(둘 다 `@Component`) —
  별도 registry/factory 클래스 없이 리스트를 순회해 `supports()`가
  true인 첫 구현체에 위임.
- 지원하지 않는 확장자는 이 서비스가 아니라 §5의 업로드 서비스가 먼저
  걸러낸다(아래 검증 순서 참고) — 이 서비스에 도달했다면 확장자는 이미
  `pdf`/`docx` 중 하나로 확정된 상태.

### 5. `SourceDocumentService.createFromUpload(MultipartFile, DocumentType)` — 검증/추출/저장 순서

**중요 — `@Valid` 우회 문제 확인 및 대응**: 기존
`SourceDocumentController.create()`의 `@Valid`는 Spring MVC가
`@RequestBody`를 JSON에서 객체로 바인딩하는 시점에만 적용되는
`RequestResponseBodyMethodProcessor`의 동작이다. 이 프로젝트는
`SourceDocumentService`에 `@Validated`를 붙이지 않았고
`create(SourceDocumentCreateRequest request)` 파라미터에도 `@Valid`가
없다(코드로 직접 확인 완료) — 즉 **`createFromUpload()`가 내부적으로
`SourceDocumentCreateRequest`를 수동으로 만들어 기존 `create()`를 직접
호출하면, record에 붙은 `@NotBlank`/`@Size`/`@NotNull` 제약은 자동으로
재검증되지 않는다.** 따라서 `createFromUpload()`는 `create()`를 호출하기
**전에** 아래 검증을 명시적으로 직접 수행해야 한다(기존 `create()`
자체나 `SourceDocumentCreateRequest`는 수정하지 않는다 — 검증 책임을
업로드 경로 안에 추가하는 것으로 해결한다).

순서:

1. **파일 존재/empty 검증**: `file.isEmpty()`면 400.
2. **크기 검증(애플리케이션 레벨, defense-in-depth)**: `file.getSize() >
   10 * 1024 * 1024`면 413(§3의 multipart 설정과 별개로 서비스 자체
   상수로 재검증 — 사용자 명시 요구사항).
3. **확장자 검증**: 원본 파일명에서 확장자를 추출해 소문자 비교,
   `pdf`/`docx`가 아니면 400.
4. **Content-Type 검증**: `MultipartFile.getContentType()`이 예상 값
   (`application/pdf` / `application/vnd.openxmlformats-officedocument.wordprocessingml.document`)과
   다르면 400 — 클라이언트가 보낸 값을 절대적으로 신뢰하지 않고, 아래
   매직바이트 검증과 함께 이중으로 사용한다.
5. **매직바이트 검증**: 파일 내용 앞부분을 읽어 PDF는 `%PDF-`로
   시작하는지, DOCX는 ZIP local file header(`PK\x03\x04`)로 시작하는지
   확인 — 불일치 시 400("확장자와 실제 파일 내용이 일치하지 않습니다"
   류의 고정 메시지).
6. **추출**: `DocumentTextExtractionService.extract(extension,
   inputStream)` 호출. `DocumentExtractionException` 발생 시 400으로
   변환(§8 로그 정책 준수).
7. **rawText blank 검증**: 추출된 텍스트가 공백만 있거나 비어 있으면
   400 "extractable text가 없습니다"(OCR 시도 없음).
8. **rawText 길이 검증**: 50,000자 초과 시 400, 저장하지 않음(truncate
   없음 — 사용자 확정 정책).
9. **fileName 길이 검증**: `MultipartFile.getOriginalFilename()`이
   255자를 초과하면 400 — 기존 `SourceDocumentCreateRequest.fileName`의
   `@Size(max=255)` 제약이 우회되므로 여기서 명시적으로 재현한다.
   originalFilename은 경로 문자열이 들어와도(`../../secret.pdf` 등)
   sanitize하지 않고 metadata 문자열 그대로 사용한다(파일시스템 접근에
   쓰이지 않음, §9 참고).
10. 위 검증을 모두 통과하면 `create(new SourceDocumentCreateRequest(
    fileName, documentType, rawText))`를 그대로 호출 — 해시 계산/저장
    로직을 복제하지 않고 재사용한다.

`documentType`은 컨트롤러의 `@RequestParam DocumentType documentType`
(필수, 자동 추론 없음)으로 받는다 — 값이 없거나 유효하지 않은 문자열이면
Spring MVC 기본 예외 처리(`MissingServletRequestParameterException`/
`MethodArgumentTypeMismatchException`, 둘 다 `DefaultHandlerExceptionResolver`가
기본으로 400 처리)로 충분하며, 별도 코드가 필요 없다(기존 GET 필터
파라미터와 동일한 방식).

### 6. Controller

```java
@PostMapping(value = "/upload", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
@ResponseStatus(HttpStatus.CREATED)
public SourceDocumentDetailResponse upload(@RequestParam MultipartFile file,
                                            @RequestParam DocumentType documentType) {
    return service.createFromUpload(file, documentType);
}
```
`POST /api/career/imports/documents/upload` — 기존
`POST /api/career/imports/documents`(rawText 직접 등록)와 같은 리소스
아래 별도 엔드포인트로 추가한다. 응답은 기존 `SourceDocumentDetailResponse`
그대로 재사용(신규 DTO 없음).

### 7. 원본 binary 미저장 (ADR-0023)

`MultipartFile`의 `InputStream`은 추출에만 사용하고 어디에도 저장하지
않는다 — 로컬 파일시스템 경로, DB bytea 컬럼, object storage 전부 만들지
않는다.

### 8. Privacy / 로깅

- `rawText`(추출된 텍스트), 파일 binary, 파서 예외의 raw 메시지를
  `log.info`/`log.debug`/`log.warn` 어디에도 원문 그대로 출력하지 않는다
  (PKB-005/006과 동일 등급 원칙).
- 파서 실패를 로깅할 때는 파일명 원문 대신 길이/확장자/documentType/
  예외 클래스 simple name 정도만 남긴다.
- 클라이언트에게 반환하는 에러 메시지는 이 명세에 정의된 고정 문자열만
  사용하고, PDFBox/POI 예외의 `getMessage()`를 그대로 응답 body에
  포함하지 않는다(문서 내용 일부가 파서 예외 메시지에 섞여 나올 수
  있음).

### 9. fileName / 파일 저장 정책 재확인

- `fileName`은 metadata 문자열일 뿐 파일시스템 경로로 절대 사용하지
  않는다 — path traversal 방어 로직이나 서버 파일 저장 기능은 만들지
  않는다(단, §5-9의 255자 길이 검증은 수행).

## Out of Scope

- LLM 호출/structured extraction/`ImportCandidate` 자동 생성(PKB-008 후보).
- OCR, 이미지 분석, 스캔 PDF 처리.
- TXT/DOC/HWP/HWPX 등 다른 형식 지원.
- 원본 파일 영구 저장(filesystem/DB/object storage).
- antivirus/malware scanner/sandbox 프로세스/CDR.
- rawText 50,000자 초과 문서의 chunking/분할 저장(PKB-008 영역).
- 파일명/내용 기반 documentType 자동 추론.
- 이메일/전화번호 등 개인정보 자동 추출.
- 사용자 인증/다중 사용자, Frontend, Calendar/알림, embedding/pgvector,
  JobPosting 매칭, 자기소개서 생성.

## Technical Notes

- ADR-0023을 구현 전에 먼저 읽는다.
- PDFBox `3.0.8`, POI(`poi-ooxml`) `5.5.1` — 정확한 버전 문자열을
  `build.gradle`에 명시(Spring Boot BOM이 관리하지 않음, Maven Central
  조사로 확인 완료).
- multipart 자동구성을 위한 신규 dependency는 없다 —
  `spring-boot-starter-web`이 이미 전이의존성으로 `spring-boot-servlet`
  (`MultipartAutoConfiguration` 포함)을 갖고 있음을 확인했다.
- 테스트용 PDF/DOCX는 **실제 사용자 문서를 절대 사용하지 않는다** —
  PDFBox(`PDDocument` 생성 후 `save()`)와 POI(`XWPFDocument` 생성 후
  `write()`)로 테스트 코드 안에서 직접 합성 fixture를 만든다(바이트
  배열/`ByteArrayInputStream`). 손상 파일 fixture는 유효한 PDF/DOCX를
  만든 뒤 바이트 일부를 의도적으로 깨뜨리거나, 아예 임의 바이트열에
  `.pdf`/`.docx` 확장자만 붙이는 방식으로 구성한다.
- `MaxUploadSizeExceededException`이 Spring Framework 7의
  `ErrorResponse`를 구현해 기본적으로 413을 반환한다는 점을 실제 통합
  테스트로도 검증한다(가정에만 의존하지 않는다).
- `SourceDocumentService.create()`/`SourceDocumentCreateRequest`는 수정하지
  않는다 — 검증 책임은 전부 `createFromUpload()`에 추가한다.
- 신규 production dependency 2개(PDFBox, POI) 외에는 추가하지 않는다.
